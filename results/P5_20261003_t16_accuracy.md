## 4. 決め手になった測定

### 4.1 正規化: NPU は正確、PC の CPU は画像の行で切れる

4 段目で取った層 0・1 の途中の値（`work/l0probe/t16_{plain,taps}_{cpu,npu}.npz`、問題 syn_nav_S）から計算した。端末の追加の実行は無い。

**(a) 重みのない正規化（V の正規化）の出力**。行ごとの二乗平均の平方根は、正しく計算すればちょうど 1 になる。

| 層 0 の V（行ごとの二乗平均の平方根） | NPU（正規化を RmsNorm にまとめた版） | PC の CPU |
|---|---|---|
| 文字 16 行のまとまり | 全部 1.000 | 全部 1.000 |
| 文字 8 行＋画像 8 行 | 全部 1.000 | 文字 1.000、**画像 0.62〜1.00**（8 行中 7 行が 1 未満） |
| 画像 16 行 | 全部 1.000 | **0.56〜0.93** |

**(b) 重みのある 3 つの正規化**（注意の後・MLP の前・MLP の後）。「入力 × 1/√(入力の二乗平均＋eps) × 重み」を理想として、それぞれの側の入力から計算した値と比べた差（行ごとの中央値）。

| まとまり | PC の CPU ↔ 理想 | NPU（RmsNorm）↔ 理想 |
|---|---:|---:|
| 文字 16 行 | 0.03〜0.05% | 0.01〜0.05% |
| 文字 8 行＋画像 8 行 | 2〜21% | 0.02〜0.06% |
| **画像 16 行** | **29〜63%** | **0.02〜0.07%** |

**CPU が切れる所の例**（画像 16 行のまとまり）:

| 正規化 | 何が起きるか | CPU の 1/√ ÷ 理想 |
|---|---|---:|
| 注意の後 | x² の目盛りの上限が 474。画像の行の本当の x² の最大は 527〜726 → 平均が 0.45〜0.67 倍に | 1.22〜1.49 倍 |
| MLP の前 | 平均は合う（0.998〜1.000 倍）のに 1/√ が小さい。その先（√ か 1/√）の目盛りで切れているとみられる | 0.62〜0.86 倍 |
| MLP の後 | 画像の行は値が小さい（x² の最大 1.4 万〜12 万。文字の行は 22 万〜350 万）→ 1/√ が大きくなり、目盛りの上限で切れているとみられる（平均は 1.00〜1.04 倍で合う） | 0.26〜0.76 倍 |

**理由**: 正規化の途中の値（x²・平均・√・1/√）の目盛りは、文章グラフを作ったとき（EdgeSLM_AndroidGemma4）に**文章だけ**を通して決めた。
画像の行は通していないので、範囲からはみ出す。NPU では変換器（QAIRT）が「x² → 平均 → +eps → √ → 1/x → ×重み」の並びを HTP の RmsNorm 1 つにまとめ、
途中の目盛りを使わずに計算するので害がない。切れるのは、PC の ORT（CPU）で量子化済みグラフをそのまま動かしたときと、
正規化をばらしたまま変換したグラフ（t16f）を NPU で動かしたときだけ。

### 4.3 NPU どうしで比べる（`probe_rows --self`、元の t16、3 問 × 5 行）

同じトークンを「まとまりの中の行 r」と「1 行だけ」（手前の行の K/V は、自分がまとまりの中で作った値を入れる）で通し、**同じ側どうし**で比べた。
PC の CPU を基準にしないので、4.1 の誤りの影響を受けない。

| | 端末の NPU どうし | PC の CPU どうし |
|---|---:|---:|
| logits の差（0 行目） | 9.1% | **0.0%**（ビット一致） |
| logits の差（1 行目以降） | 27.1% | 12.8% |
| 1 位の語が同じ | **15/15** | 15/15 |
| 上位 5 語の重なり | 4.1/5 | 4.7/5 |
| 1 行目以降の K の差（層 0 → 1 → 4 → 9 → 14） | 0.0 → 4.0 → 5.6 → 7.1 → 5.9% | 0.0 → 1.8 → 3.8 → 7.0 → 5.8% |
| 1 行目以降の V の差（層 0 → 1 → 4 → 9 → 14） | 0.0 → 15.1 → 11.7 → 9.9 → 9.4% | 0.0 → 3.7 → 6.3 → 9.0 → 10.7% |
| 0 行目の K の差（層 0・1 → 2 → 9 → 14） | 0.0 → 2.2 → 10.1 → 8.2% | 全部 0.0% |

- **PC の CPU どうしでも、1 行目以降は logits が 13% 違う**。「1 行だけ」は手前の行の K/V がいったん出力の目盛りで丸められて入力に戻るが、
  「まとまりの中」は丸め直さずに使う。量子化したグラフでは 2 つは同じ計算ではなく、その違いが層を通るうちに育つ
- **深い層（9〜14）の K/V の差は NPU と CPU で同じ水準**（K 4〜7%、V 9〜11%）。NPU だけが急に大きくなる層は無い
- NPU だけに見える違い: (a) 浅い層で差が早く出る（層 1 の V が 15%）、(b) **0 行目の結果が、同じまとまりのほかの行の中身で変わる**（層 2 から）。
  0 行目は後ろの行を見ないので、数学的には変わらないはず。NPU の層 1 の中のどこかの演算で、行どうしがわずかに影響し合っている（**どの演算かは特定していない**）

### 4.4 丸めの違いが育つ大きさ（`diag_t16fix`、PC の CPU だけ）

| 比べたもの（同じ入力） | logits の差 |
|---|---:|
| 元のグラフをもう 1 回 | 0.0000% |
| 元のグラフの入力の埋め込みを相対 1e-6 揺らす | 0.0000%（入口の 16bit の丸めで消える） |
| **元のグラフ ↔ 元のグラフ（ORT のグラフ最適化を切る）** | **14.2%** |
| 元のグラフ ↔ t16f のグラフ | 18.1%（1 回目）・14.2%（2 回目） |

t16f の書き直しで最初に違ったのは、6 番目の平均の 16 個の値のうち 1 個が**ちょうど 1 目盛り**ずれた所（丸める前の差 4e-7＝足す順序の違い）。
それが 6e-6 → 2e-3 → 2e-2 → 18% と育つ。**「2 つの実行の logits の差が 1〜2 割」は、正しい計算どうしでも出る大きさ**なので、
この水準より下では不具合の物差しにならない。版どうしは答え（点・1 位の語）で比べる。

## 7. 学んだこと

1. **基準にする側が正しいかを先に確かめる。** 「NPU と PC の CPU の差」を NPU の誤差と読んだが、切れていたのは CPU だった。
   正規化なら「出力の二乗平均が 1 か」「入力から計算した理想の値と合うか」のように、どちらの側にも当てられる物差しがある
2. **較正に通していない種類の入力（ここでは画像の行）では、量子化の目盛りが足りないことがある。** 変換器が演算をまとめる所は途中の目盛りを使わないので、
   まとめた方が正確なこともある。「まとめられた演算＝怪しい」とは限らない
3. **部品ごとの誤差が小さくなることと、答えが良くなることは別。** 小さいグラフで差が減っても、全体で 126 問を解かせて確かめる
4. **量子化したグラフの 2 つの実行の差は、丸め 1 目盛りの違いから 1〜2 割まで育つ。** 同じグラフを設定違いで 2 回動かした差を、物差しの目盛りとして先に測る
5. **比べる条件をそろえる。**「まとまりの中」と「1 行だけ」で、手前の行の値がどちらのものかが違っていた
6. **答えの 1 トークン目の一致は粗い物差し**（半分は同じ語で始まる）。点と答えの中身を合わせて見る
7. **直しは 1 つずつ入れて評価する。** 2 つ同時に入れた版（t16f）では、どちらが効いたのか分からなくなった
