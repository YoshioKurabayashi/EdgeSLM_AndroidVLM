## 1. 結論

| 問い | 結果 |
|---|---|
| v68 に渡せる形になったか | **なった。** 2 版とも C-1（float の区間なし）・C-5 合格、C-8 の右辺 32/32 を 8bit に。大きさ 149.9MiB（float の 587MiB の約 1/4） |

| **答えの品質（Q12）** | **SRQ ありの版の特徴で 44/123**（基準 42/123、量子化前の自前 46/123）。基準との入れ替わり 8↑・6↓で偏りなし → **合格**（6 節） |

## 2. 量子化の段ごとの結果

| 段 | 結果 |
|---|---|
| 前処理・較正・量子化（`p2b_ops.prepare`、scheme `a16w8_rhs8`） | `ready_for_convert`。較正は評価用と別の 64 枚。重み 114 本を出力チャネルごとに量子化（この段では仮の INT4） |
| QAT の値の書き込み（`qat_inject_vit`） | 114 本を書き込み、114 本とも INT8 に。INT4 の残り 0 |
| 　うち QAT の 112 本 | 整数・スケールとも QAT と**完全一致**（重みの誤差 0） |
| 　うち float の 2 本（作り直し） | パッチの埋め込み `input_proj` 相対誤差 0.98%、射影層 `embedding_projection` 1.10%（INT8・出力チャネルごと。上限 5% の内） |
| 　SRQ（SRQ ありの版だけ） | 入力側 112・出力側 112（想定どおり）。SRQ なしの版は 0/0 |
| C-8（`downgrade_actact_rhs`） | 活性×活性の行列積の右辺 32（16 層 ×2）をすべて 8bit に。対象外 0 |
| C-1・C-5（`verify_artifacts`） | 2 版とも合格（「計算ノード間・グラフ I/O 境界ともに float の残存はない」） |
| 大きさ | 2 版とも 149.9MiB（SRQ ありは入力側の Q/DQ が 112 組多いぶん 31KB 大きい。出力側の 112 組は、16bit の Q/DQ をその場で 8bit に書き換えたので数は同じ） |

大きさの見当: 1 層あたり attention 4 本（768×768）＋ MLP 3 本（768×3072）＝ 944 万、16 層で 1.51 億。1 つ 1 バイトで 144MiB、
これにパッチの埋め込み・射影層・定数を足して 150MiB。重みが確かに 8bit で入っていることの裏付けになる。

## 3. PC（ORT CPU、最適化なし）での精度 — 評価用 16 枚

| 比較 | 相対 L2 の平均 | cos 最小 | cos 中央値 |
|---|---:|---:|---:|
| 書き出した float の ONNX ↔ HF（SRQ なし） | 0.0000019 | 0.99999999993 | 1.0000 |
| **SRQ なしの版 ↔ HF（SRQ なし）** | **0.037** | **0.9972** | **0.9993** |
| SRQ なしの版 ↔ float の ONNX | 0.037 | 0.9972 | 0.9993 |
| SRQ ありの版 ↔ HF（SRQ あり） | 0.354 | 0.814 | 0.918 |
| SRQ ありの版 ↔ HF（SRQ なし） | 0.524 | 0.703 | 0.861 |
| （参考、2-1）自前の float・SRQ あり ↔ HF（SRQ あり） | 0.32 | 0.84 | — |
| （参考、2-1）HF の SRQ あり ↔ なし | 0.52 | — | 0.86 |

### 3.1 画像ごとの cos

| 画像 | SRQ なしの版 ↔ HF（SRQ なし） | SRQ ありの版 ↔ HF（SRQ あり） |
|---|---:|---:|
| vg_00 / vg_13 / vg_26 / vg_39 | 0.9994 / 0.9989 / 0.9995 / 0.9990 | 0.928 / 0.893 / 0.935 / 0.915 |
| wild_00 / wild_18 / wild_33 / wild_49 | 0.9985 / 0.9990 / **0.9972** / 0.9993 | 0.901 / **0.814** / 0.913 / 0.933 |
| car_01a / car_05a / car_09a / car_13a | 0.9994 / 0.9988 / 0.9993 / 0.9995 | 0.902 / 0.843 / 0.918 / 0.893 |
| syn_nav_L / syn_sign / syn_aircon / syn_paragraph | 0.9996 / 0.9992 / 0.9994 / 0.9996 | **0.980 / 0.975 / 0.977 / 0.987** |

### 3.2 読み方

- **算術の誤差は小さい。** SRQ なしの版は、揺れの源（SRQ）が無いので、量子化（16bit の活性・8bit の重み・8bit の右辺）の誤差だけが見える。
  それが cos 0.997〜0.9996。16 枚のどれも 0.99 を大きく上回る
- 相対 L2 3.7% の内訳は**測っていない**。候補は (1) C-8 で 8bit にした K と V（q/k/v の正規化の後なので値の幅は狭いが、8bit は 256 段しかない）、
  (2) float から作り直した 2 本の重み（約 1%）、(3) 16bit の活性（65,536 段なので小さいはず）。合格しているので、いまは分けない
  （端末の誤差が大きかったときに、この順で疑う）
- **SRQ ありの版の cos 0.81〜0.92 は、量子化のせいではない。** 量子化する前の自前の float（SRQ あり）でも HF と 0.84 まで離れていた（2-1 の 3.2 節）。
  「SRQ ありの版 ↔ HF（SRQ なし）」の中央値 0.86 も、HF 自身の SRQ あり ↔ なし（0.86）と同じ。量子化はこの揺れにほとんど上乗せしていない
- 合成画像（syn_*、平らな色と文字）は SRQ の揺れが小さい（0.975〜0.987）。写真は 0.81〜0.94。理由は確かめていない
  （写真の方が活性の値がばらけて、8bit の境目にかかるものが多い、という見当）
- ORT CPU で 1 枚 1.7 秒（float は 0.76 秒）。QDQ を「丸めて戻す」計算として素直に回しているだけなので、端末の時間の目安にはならない

## 5. 実行時の不具合と修正（2026-09-28）

`eval_qdq_vit feats` が `ModuleNotFoundError: No module named 'torchvision'` で止まった。HF の Gemma4Processor は画像の前処理に
torchvision を使うが、EdgeSLM_Android の venv（ONNX の評価に使う）には torchvision が無い（venv にパッケージは足さない約束）。
`acc` は capture の pixel_values（Phase 1 の venv で HF から取ったもの）を使うので、この問題に当たらなかった。

直し方: 前処理を numpy で書いた（`hf_vlm.pixels_fixed_np`）。固定の格子にちょうど収めた画像なら、HF のプロセッサがやることは
「大きさを変えない・画素 × 1/255（float32）・(縦, 横, パッチ内 y, パッチ内 x, 色) の順に並べる」だけ（transformers 5.14.1 のコードで確認）。
`feats` は毎回、最初に capture の評価用 16 枚で HF の値と照合し、違えば止まる。
事前に確かめた結果: **16 枚すべてでビット単位で一致**（差の最大 0）。Pillow は 2 つの venv とも 12.3.0 で、レターボックスの縮小（BICUBIC）も同じ。

この numpy の前処理は、端末のアプリ（Phase 3）で前処理を書くときの手本にもなる。

入れ替わり（1 問ずつの正誤）:

| 比べる相手 | 上がった | 下がった | 答えの文が完全一致 |
|---|---:|---:|---:|
| HF（基準） | 8 | 6 | 28/126 |
| 自前の float・SRQ あり | 4 | 6 | 25/126 |

- **量子化しても答えの品質は変わらない。** 44 は基準（42）と量子化前（45〜46）の間。入れ替わりは上下ほぼ同数で、Phase 1 で見た SRQ の揺れ（1 割ほど）の範囲
- 答えの文がそのまま一致するのは 2 割ほど。特徴が少し違えば言い回しは変わるが、正誤はほとんど変わらない（Phase 1 の 1 トークンずつの流し方と同じ傾向）
- これで 2-2 は合格。端末（2-4・2-5）でも同じ物差し（全体の点と入れ替わりの偏り）で比べる
