## 2. まとめ読み（16 トークン版の 1 本）

### 2.1 なぜ 1 本で両方なのか（以前の検証から）

| 分かっていること（EdgeSLM_AndroidGemma4 P6） | 意味 |
|---|---|
| 1 回で 16 トークンを読むグラフは、1 回の時間が 1 トークン版の **1.08 倍**（9 層で実測。1 回の時間の大半は重みを読む時間） | 16 トークンまとめて読めば、1 トークンあたり 15 分の 1 |
| 読む用と答えを作る用の 2 つを同時に持つのは **RAM が足りず無理**。重みを共有する仕組みは v73 以降だけ | 2 つ持つ案は使えない |
| グラフを持ち替えると 2.3〜2.5 秒 | 1 問ごとに持ち替えると、最初の文字まで 5 秒前後にしかならない |

→ **16 トークン版の 1 本だけを持ち、答えを作るときは 1 トークンだけ入れて残り 15 行を空で回す**。答えは 1.08 倍遅くなるが、
持ち替えが要らず、プロンプト約 109 トークンは 7 回（約 0.6 秒）で読める。

### 2.2 グラフの入出力（`g4t16_W256`）

| 入力 | 形 | 中身 |
|---|---|---|
| `inputs_embeds` | [1,16,1536] | 16 行。使わない行は 0 |
| `ple_tok` | [1,16,35,256] | 同上 |
| `cos_s`/`sin_s`・`cos_g`/`sin_g` | [1,16,1,256]・[1,16,1,512] | 行ごとの位置の表 |
| `attn_mask` | [1,16,1,256] | 行ごとのマスク（下の 2.3） |
| `past_k_i`/`past_v_i`（i = 0〜14） | [1,1,**240**,hd] | それまでの K/V（右詰め、最大 240 トークン） |
| `logit_sel` | [1,16,1] | **どの行の答え（logits）が欲しいか**の 1 つだけ 1、ほかは 0 |

| 出力 | 形 | 中身 |
|---|---|---|
| `logits` | [1,**1**,262144] | `logit_sel` で選んだ行だけ（16 行分を出すと 16MB になり、NPU から写すだけで数 ms かかる） |
| `present_k_i`/`present_v_i` | [1,1,**16**,hd] | **この回に入れた 16 行ぶんの新しい K/V だけ** |
| ★実装: `present_k/v_13`・`_14` | [1,1,**256**,hd] | 後ろの層（15〜34）が使い回す層 13・14 は**窓全体**（past 240＋新 16）。端末は「後ろから 16 行目」から新しい行を読む（下の 4.） |

1 トークン版との違い（あえて変えたところ）:

1. **新しい K/V だけを出す**。1 トークン版は「窓全体（256 スロット）」を出し、端末はそれを次の past にそのまま使っていた（写さない）。
   16 トークン版で答えを作るときは、16 行のうち本物は 1 行だけなので、窓全体をそのまま使えない（空の 15 行が窓に入ってしまう）。
   どのみち端末が「本物の行だけを past に足す」処理をするので、出力は新しい 16 行だけで足りる。出力の大きさは 9.4MB → 0.6MB
2. **注意の窓は 256 のまま**（past 240 ＋ 新しい 16）。softmax の長さ・マスクの形が 1 トークン版と同じなので、量子化の振る舞いも近い
3. **出力層の前で 1 行だけ選ぶ**。~~`logit_sel` を掛けて 16 行を足す（Mul と ReduceSum）~~ → ★実装: **最後の層のかたまり E（層 29〜34）の出口で、行列積 `h^T @ logit_sel`**（[1,1536,16]×[1,16,1]）。
   右辺が logit_sel（0 と 1 だけ）なので、C-8 で 8bit に落ちても正確。ReduceSum を ORT の量子化が扱うか確かでなかったこと、出力層のかたまりの中で選ぶとグラフ入力が Transpose に直接入って量子化されない（C-1）ことから変えた。
   これで出力層（H）は 1 トークン版と同じ形になり、**Gemma4 の `g4head_L256_final_qdq.onnx` を複製して使う**
4. KV を使い回す層（15〜34）は、層 13・14 の「past 240 ＋ 新しい 16」をそのまま使う。~~かたまり B はこれを `window_k_13` などとして後ろのかたまりへ渡し、繋いだ後はグラフ出力から外す~~
   → ★実装: 層 13・14 の present を窓全体 [1,1,256,hd] にして、1 トークン版と同じ名前の繋ぎ方（`present_k_13` → `shared_k_13`）のまま `merge_chunks`（複製、無改造）で繋ぐ。グラフ出力にも残る（出力は合計 約 3.1MB）

### 2.3 マスクと位置（端末の C++ が作る）

窓のスロット j（0〜255）: j < 240 は past のスロット j、j ≥ 240 はこの回の j−240 行目。

- 本物の行 t（0 ≤ t < n）: past のうち有効な右端 `n_valid` 個（[240−n_valid, 240)）と、この回の 0〜t 行目（[240, 240+t]）を開ける。ほかは −60
- 空の行（t ≥ n）: 0 行目と同じマスク（出力は使わないが、NaN を出さないため）
- 位置の表: 本物の行はその絶対位置、空の行は最後の本物の行と同じ
- 回したあと: 各層の past を `n` 個左へずらし、`present` の 0〜n−1 行目を右端に書く。`n_valid = min(n_valid + n, 240)`
- 覚えていられるのは直近 240 トークン（1 トークン版は 256）。VLM のプロンプト約 113 ＋ 答え 96 以下なので足りる

**Gemma4 のプロジェクトは変えない**（道具は複製して md5 を記録。モデルと取ってある状態は読むだけ）。

### 2.5 端末（C++）

`generate_kv` に**複数トークンの経路**を足す（モデルの `inputs_embeds` が [1,T,H] で T>1 のとき）。1 トークン版の経路は変えない。

| 機能 | 16 トークン版での扱い |
|---|---|
| プロンプトを読む | 16 個ずつ（最後は端数）。最後の回だけ `logit_sel` を最後の本物の行にして答えの 1 つ目を取る |
| 答えを作る | 1 個ずつ（0 行目だけ本物、`logit_sel` は 0 行目） |
| 画像の特徴 | 1 トークン版と同じく、画像トークンの位置は特徴をそのまま入れ、PLE は pad の行 |
| 前のターンの続き（`reuse_cache`・`prompt_is_delta`） | 同じ仕組み（KvCarry）で past と位置を持ち越す |
| 途中経過（1 文字ずつの表示） | 同じ（GenProgress） |
| 使わない機能 | `pin_pos0`・`pos0_kv`（Qwen 用）は 16 トークン版では使えない（指定されたらエラー） |
| 念のため | 窓全体を出す形（1 トークン版と同じ `present` [1,1,L,hd]）のモデルでも動くようにしておく（変換で困ったときの逃げ道） |

## 3. 画像エンコーダの常駐

いまは写真ごとに別プロセス（`:probe`）の RunnerService2 を起こし、画像エンコーダ（152MiB）を開いて 1 回動かして閉じている（1.1 秒のうち NPU は 0.17 秒）。

- RunnerService に「開いたままにする」指定（job の `keep_session: true`）を足す。同じモデルなら前に開いたものを使い、閉じない。
  持っておく場所はプロセスごとの変数なので、Service が止まってもプロセスが生きている間は残る
- `:probe` のプロセスが OS に止められたら（裏で待っているだけなので真っ先に止められる）、次の写真で開き直す（いまと同じ 1.1 秒）
- デモ画面は、文章側を開き終えたあとで画像エンコーダを「開くだけ」の job で先に開いておく（開くときのメモリの山を重ねない）
- メモリ: 文章側 1,467MiB（主プロセス）＋画像エンコーダ 152MiB（`:probe`）の同居は 2-4 で確認済み
