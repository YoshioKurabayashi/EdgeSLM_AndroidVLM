## 1. 何をするシステムか

スマホのカメラで撮った写真について、日本語の質問に日本語で答える。**インターネットを使わず、行列の計算はすべてスマホの NPU で行う**
（機内モードでも動く）。PC は、モデルを作る・スマホに送る・評価する・録画するための道具として使う。

| 対象 | 対象外（いまの版） |
|---|---|
| 写真 1 枚あたり画像トークン 70（横長の固定の格子 21×30 パッチ、336×480px） | 280 トークン（細部の読み取り）・縦長用の格子（2-6） |
| 1 枚の写真への質問と、同じ写真への追加の質問 | 連続フレーム（動画を数秒おきに説明） |
| 日本語の質問・答え | 音声 |

## 2. 全体の構成

```
┌─────────────────────────── PC（Windows、PowerShell）───────────────────────────┐
│ app/pipeline/                                                                    │
│   作る:   build_t16（16 トークン版の文章モデル）・export_vit 等（画像エンコーダ）   │
│           → QAIRT で v68 の context binary に変換                                 │
│   送る:   setup_vlm_demo（モデル・表・トークナイザ・設定をスマホへ）              │
│   確かめる: device_vlm（prep / eval / uicheck / holdcheck）・check_t16・ref_vlm    │
│   撮る:   record_demo（画面の録画とログ）                                          │
└───────────────────────────────────┬──────────────────────────────────────────────┘
                                    │ USB（adb push / pull / am start）
┌───────────────────────────────────┴────── スマホ（org.edgeslm.vlm）───────────────┐
│ 主プロセス                                            別プロセス（:probe）         │
│ ┌──────────────────────────────────────┐   job(file)  ┌──────────────────────────┐│
│ │ VlmActivity（デモ画面）               │ ───────────▶ │ RunnerService2           ││
│ │  写真の読み込み・EXIF（Kotlin）       │              │  画像エンコーダ 152MiB    ││
│ │  前処理（C++ nativeVlmPrep）          │ ◀─────────── │  （NPU、開いたまま）      ││
│ │  トークナイザ（Kotlin）               │  result(file) └──────────────────────────┘│
│ │  文章側 generate_kv（C++ nativeRunJob）│                                          │
│ │   Gemma 4 16 トークン版 1,467MiB（NPU、開いたまま）                               │
│ └──────────────────────────────────────┘                                          │
│ RunnerActivity / RunnerHoldActivity → RunnerService（PC からの job の入口。評価用） │
└───────────────────────────────────────────────────────────────────────────────────┘
```

- **NPU のメモリはプロセスごとに約 1,710MiB まで**（EdgeSLM_AndroidScale P0A）。文章側（1,467MiB）と画像エンコーダ（152MiB）は別プロセスに置く
- 2 つのモデルはどちらも**開いたまま**にする（文章側は画面を開いたとき、画像エンコーダはその直後に「開くだけ」の job で）
- CPU が受け持つのは、写真の復号・前処理・トークナイザ・埋め込みと PLE の表引き・KV キャッシュの出し入れ・答えの選択（argmax）。
  **行列の計算はすべて NPU**（EPContext で CPU への逃げ道なし＝strict）

## 4. 処理の流れ

### 4.1 起動

1. `VlmActivity.onCreate`: `jobs/vlm_demo.json` を読む → 画面を作る
2. 裏のスレッドで文章側を開く（`nativeCreate`、約 2.3 秒。開く間は一時的に約 3GB 使う）。画面は前にあるので OS に止められにくい（優先度 0）
3. 開き終わったら、画像エンコーダを「開くだけ」の job（`task: "open"`・`keep_session: true`）で RunnerService2 に渡す（結果は待たない）
4. 画面の上の行が「準備できました（全部 NPU）」になる

### 4.2 写真 → 画像の特徴

1. 「写真を撮る」→ カメラアプリ（MediaStore の `Pictures/VLMDemo` に保存させる）
2. 戻ったら裏のスレッドで: JPEG を 2 の累乗で間引いて復号（短い辺が 672 以上に収まる範囲、12MP なら 1/4）→ EXIF の向きを反映 → RGB のバイト列
3. 前処理（C++）: 縦横比を保って 336×480 に縮小（BICUBIC）→ 余白を黒 → 16×16 のパッチ → ÷255 → `inputs/vlm/cam_pix.bin`（[630,768] float32）
4. 文章側が開いている途中なら、開き終わるまで待つ（開くときのメモリの山を重ねない）
5. `jobs/vlm_vit.json`（`task: "infer"`・`keep_session: true`）を書いて RunnerService2 を起こし、`out/last_result.json` に同じ `job_id` が書かれるのを待つ（上限 30 秒）
6. 特徴のファイル（`out/vlm/…_cam_image_embeds.bin`、[70,1536] float32）の場所を覚え、質問できる状態にする

### 4.3 質問 → 答え（1 問目）

1. プロンプトの ID を作る（HF の chat template と同じ並び）:
   `<bos><|turn>system\n{system}<turn|>\n<|turn>user\n` ＋ `<|image>`(255999) ＋ 画像トークン(258880)×70 ＋ `<image|>`(258882) ＋ `{質問}<turn|>\n<|turn>model\n`
   （特殊トークンの所で分けてトークン化するので、全体を一度にトークン化したのと同じ ID になる。約 104〜120 個）
2. `generate_kv` の job を作り（5.2 節）、裏のスレッドで `nativeRunJob`。画面は 50ms ごとに `nativeProgress` を読んで 1 トークンずつ表示
3. C++（複数トークンの経路。モデルの `inputs_embeds` が [1,16,H] なので自動で選ばれる）:
   - プロンプトを **16 個ずつ**読む（107 個なら 7 回）。各行: 文章の ID は埋め込みの表（2bit）を引いて ×√1536、**画像トークンの位置は特徴の 1 行をそのまま**。PLE は表を引く（画像の位置は pad の行）。位置は絶対位置
   - マスク: 行 t は「past の有効な右端 n_valid 個」と「この回の 0〜t 行目」だけを開ける（ほかは −60）。空の行は行 0 と同じ
   - 回したら、各層の past を n 個左へずらし、present の新しい n 行を右端に書く（`n_valid ≤ 240`）
   - 最後の回は `logit_sel` を最後の本物の行にして、答えの 1 つ目を取る
   - 答えは **1 個ずつ**（本物 1 行＋空 15 行）。`stop_ids`（106・1・50）か `max_new`（96）で止まる
4. 終わったら答えを表示。**上限で止まり EOS で止まっていなければ「…（長いので途中まで）」**を付ける。技術情報の 1 行（画像の秒数・最初の文字まで・tok/s・全部 NPU か）

### 4.4 同じ写真への追加の質問

- `<turn|>\n<|turn>user\n{質問}<turn|>\n<|turn>model\n` の差分だけを送る（`reuse_cache: true`・`prompt_is_delta: true`）。C++ が前の past と位置を持ち越す（KvCarry）
- 位置が past の長さ（240）を超えたら、次の質問は写真から作り直す（画像の部分が押し出されるため）
- 新しい写真を撮ったら、会話と KV キャッシュを捨てる（`reset_cache: true`）

### 5.2 job（JSON のファイル。`jobs/*.json`）

| task | 主なキー | 誰が使う |
|---|---|---|
| `generate_kv` | `model`・`ep`・表の場所（5.1）・`prompt_ids`（または評価用の `dialogs`: `[{id, turns:[[ids]], image_features, max_new}]`）・`image_features`（特徴のファイル）・`max_new`・`stop_ids`・`mask_neg`(−60)・`reuse_cache`・`reset_cache`・`prompt_is_delta` | 画面（`nativeRunJob`）・評価（RunnerService） |
| `infer` | `model`・`ep`・`batches: [{id, inputs:{pixel_values: file}}]`・`output.dir`・`keep_session` | 画面の画像エンコーダ（RunnerService2）・照合 |
| `open` | `model`・`ep`・`keep_session: true` | 画面（画像エンコーダを先に開く） |
| `vlm_prep` | `rgb`・`width`・`height`・`grid`・`out` | 前処理の照合（PC） |

- `ep`: `{"provider":"QNN","backend":"libQnnHtp.so","options":{"offload_graph_io_quantization":"0","qnn_context_priority":"high"},"session":{"intra_op_num_threads":1}}`
- 実行時に `runtime.base_dir`（アプリの置き場）と `native_lib_dir`（FastRPC が libQnnHtp.so の実ファイルを要るため）を足す（`JsonInject`）
- `keep_session: true`: 同じモデルならプロセスの中で開いたハンドルを使い回し、job の終わりに閉じない。違うモデルが来たら前のを閉じる。job は 1 つずつ（`synchronized`）

### 5.5 PC ↔ スマホ

- ファイルは `adb push`/`pull`（`/sdcard/Android/data/org.edgeslm.vlm/files/…`）。同じ大きさ・md5 なら送らない
- job は `am start -n org.edgeslm.vlm/org.edgeslm.demo.RunnerHoldActivity -a org.edgeslm.demo.RUN --es job jobs/….json`（評価は画面を前に出したまま）
- PC は結果のファイルを 2 秒ごとに見て、プロセスが消えていないか（`pidof`。最初の 30 秒は 2 秒ごと、その後は 10 秒ごと）も監視する。
  消えたら理由（lowmemorykiller の行）をログから拾い、待ってやり直す（評価は 30 秒待って 2 回まで、続きから）

## 8. 設計上の判断と理由

| 判断 | 理由 | 出どころ |
|---|---|---|
| 画像エンコーダを別プロセスに | NPU の上限はプロセスごと。1 プロセスに 2 つだと余裕が少ない | Phase 2・3 |
| 固定の格子（21×30）＋レターボックス | v68 は動的な形を扱えない。70 トークンで HF の既定と品質に差なし | Phase 1 |
| 画像トークン 70 | 待ち時間と品質の兼ね合い。画面・文書の文字は 70 で足りる（実写の細部は 280 が要る） | Phase 1 |
| 文章側のグラフは Gemma4 の配線のまま | E2B は画像トークンに普通の因果マスクと 1 次元の位置を使う。HF とビット一致を確認 | Phase 1 |
| **16 トークン版 1 本で読むのも答えを作るのも** | 1 回の時間は重みを読む時間でほぼ決まる（16 行でも 1.08 倍）。2 本は RAM が足りず、持ち替えは 2.3 秒 | Phase 5 |
| 窓 256 のまま past を 240 に・出力は新しい行だけ・行の選択は最後の層の出口（右辺を logit_sel） | 量子化の振る舞いを 1 トークン版に近づける・空の行を窓に入れない・出力層を複製で使う・C-8 と C-1 を避ける | Phase 5 |
| 画像エンコーダを開いたまま | 1.1 秒のうち NPU は 0.2 秒で、残りは開く時間 | Phase 5 |
| 大きいモデルを開く間は画面を前に | 開く間は約 3GB。画面の無い Service（優先度 50）だと OS に止められる | Phase 3 |
| system 文「添付の画像を見て…」 | 126 問で 45 → 54（入れ替わり 11↑・2↓）。「判断できません」と逃げる答えが減った | Phase 5 |
| CPU への逃げ道なし（strict） | 全部 NPU で動いていることを保証し、遅い経路に落ちたことに気づけるように | EdgeSLM_Android |
| **正規化は変換器（QAIRT）がまとめる RmsNorm のまま使う（ばらして書き直さない）** | NPU の RmsNorm は理想の計算と 0.1% 未満で一致する。ばらすと、量子化済みグラフの途中の値（x²・平均・1/√）の目盛りが使われ、画像の行ではみ出して切れる（目盛りは文章だけで決めた）。ばらした版 `g4t16f_W256` は 126 問で 45 → 37、「画像が提供されていません」12 問、1 割強遅い | Phase 5 の精度の切り分け（2026-10-03） |
| **文章側は元の 16 トークン版で確定** | 1 トークン版と同等の点（45 と 48。いまの system 文で 54）、最初の文字まで 8.3 → 0.5 秒。HF と同じ答えが減ったのは不具合ではなく、主に「まとめて通す」と「1 行ずつ通す」の丸め方の違い（PC の CPU どうしでも logits が 13% 違う。1 位の語は 15/15 で同じ） | 同上（利用者の決定） |

## 9. 制約・既知の課題

| 項目 | 内容 | 対処・次の手 |
|---|---|---|
| 覚えていられる長さ | past 240 トークン（1 枚目 約 107＋答え 96 で約 200）。追加の質問であふれたら写真から作り直す | 280 トークンや長い会話には窓の大きいグラフ（L512）が要る |
| 細部の読み取り | 70 トークンでは実写の小さな文字・メーター・信号が苦手 | 280 トークン（2-6）＋まとめ読み |
| 縦長の写真 | 横長の枠に入れるので左右が黒帯 | 縦長用の格子（画像エンコーダをもう 1 本） |
| HF との一致 | **確定（2026-10-03）: 元の 16 トークン版のまま使う。下は調べた順の記録で、まとめは [P5 精度の切り分け](../results/P5_20261003_t16_accuracy.md)**。16 トークン版は HF と答えの 1 トークン目が同じ問題が 1 トークン版より少ない（97 → 78/126）。文字の読み間違いの例あり。**原因はグラフではなく端末での実行**（同じグラフを PC の CPU で動かすと HF と 13/16 一致、端末は 5/16。2026-09-30 の `diag_t16`）。**さらに分けると NPU での 16 トークン版の計算が原因で、C++ の入れ方は正しい**（`probe_t16`: Python の入れ方で NPU に通すと端末の答えを 7/7 再現。同じ入力で NPU と CPU の logits の差 中央値 62%、K/V の差は層 0 → 層 1 で 2% → 23%）。ただし**層 0〜14 のずれは 1 トークン版にも同じだけあり**、16 トークン版だけ悪いのはプロンプトの最後の回の logits（38〜61% と 14〜33%）（2026-10-01）。**原因は 2 つ**: ① QAIRT が正規化を HTP の RmsNorm にまとめるとずれる（両方の版。画像の行で大きい）、② 16 トークン版の PLE の tanh（[16×256]）が 2〜15 行目で壊れる 。小さいグラフでは「平均を行列の掛け算に」＋「tanh を 1 行の形で」で直る（層 0 の出力の画像の行 150% → 20%）。**全体を書き直した版 `g4t16f_W256`（2026-10-02）は、16 行まとめのずれは消えた（1 トークン版と 1 トークン目が同じ 80 → 101/126）が、126 問は 45 → 37/123（「画像が提供されていません」系 0 → 12 問）、1 トークン 87 → 101ms。採用しない**。PC の CPU どうしでも ORT の最適化を切るだけで logits が 14% 変わる（丸め 1 目盛りの違いが育つ）ので、NPU と CPU の「差 2 割」は不具合の物差しにならない。**2026-10-03 に訂正: ①は誤りで、ずれていたのは基準にした PC の CPU**（正規化の途中の値の目盛りが画像の行ではみ出して切れる。NPU の RmsNorm は理想の計算と 0.1% 未満で一致、CPU は画像の行で 29〜63% ずれる）。t16f は NPU を CPU の誤った値に合わせたので画像が見えなくなった。tanh だけ直した版 `g4t16t_W256` は元と同じ答え（②は効いていない）。**元の t16 をそのまま使う（1 トークン版と同等の点。t16f・t16t は不採用）** | `probe_rows --self`（NPU どうしで「まとまりの中」と「1 行だけ」を比べる）で、16 行をまとめたことによる大きな不具合は見つからなかった（1 位の語 15/15、深い層の K/V の差は PC の CPU どうしと同じ水準）。小さな違い（0 行目がほかの行の中身で少し変わる。logits で 9%）は残るが実用上の問題は無い。**元の t16 で確定** |
| PC の CPU は画像の行の基準に使えない | 量子化済みグラフを PC の ORT（CPU）で動かすと、画像の行で正規化が切れる（理想の計算との差 29〜63%。NPU は 0.1% 未満）。PC の CPU だけで解かせると「画像が提供されていません」と答える問題がある | NPU の確かめは `probe_rows --self`（NPU どうし）か理想の計算との比べで行う。CPU を基準にするなら、正規化の途中の値の目盛りを画像の行も通して決め直す（未実施） |
| 採用しなかった版のファイル | PC の `work/ops/g4t16f_W256/`・`g4t16t_W256/`（各 6.3GB）は **2026-10-03 に削除**（利用者の承認）。スマホの `models/ops/` の `g4t16f_W256_*`・`g4t16t_W256_*`（各 約 1.5GB）も同じ日に利用者が adb で消した | 結果・ログ・道具は残してある。もう一度動かすには `build_t16fix` で作り直す（各 約 4 時間） |
| 長い答え | 評価（上限 64）で約 3 割（40〜44/126）が上限で切れる。デモの上限は 96（切れたら印を出す） | system 文・上限の調整 |
| 画面のタップが効かないことがある | 2026-09-30 の 1 本目の録画で、2 枚目の写真を読み終えた後、約 16 秒間（09:36:26〜42）に約 20 回タップしても反応しなかった（その後のタップは効いた）。原因は未特定 | タップ・押されたボタン・受け付けなかった理由をログに出し、候補ボタンに押した見た目・押せないときの薄い表示を足した版（2026-09-30 10:24 の 2 本目）では再現せず、写真 2 枚 × 質問 2 つが全部通った。再発したらログで切り分ける |
| 裏のプロセスが止められる | :probe が OS に止められたら、次の写真で画像エンコーダを開き直す（1.1 秒） | そのまま（動作は続く） |
| v68 の制約 | 動的な形・重みの共有・u16×u16 の活性の行列積が使えない など（C-1〜C-14） | 本書の判断はこれを前提にしている |

cd D:\AI\source\n_chap5\EdgeSLM_AndroidVLM
