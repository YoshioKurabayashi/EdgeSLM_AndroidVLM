## 0. 要点

1. **引き継ぎメモの未確定事項 1〜4・6 は、手元の記録で埋まった**（2章）。残るのは評価データ・目標値・期限（7）と、接続方針の最終決定（5）

## 3. v68 で踏んだ制約のうち、画像エンコーダに効くもの

詳細は [EdgeSLM_Android/DoC/要件定義書.md](../../EdgeSLM_Android/DoC/要件定義書.md) 3.4節（C-1〜C-13）。

| 制約 | ViT への影響 |
|---|---|
| **C-8**: act×act の MatMul は `u16×u16` 不可、`u16×u8` のみ可（右辺を 8bit） | ViT の QK^T と PV に直撃。Gemma 4 は活性がもともと 8bit（SRQ）なので、文章側と同じやり方で通る見込み |
| **C-10**: `Expand` を含む context binary は読めない | ViT は KV ヘッド＝Q ヘッド（12/12）で GQA の複製が無い。ただし export 時に出ないかは確認 |
| **C-9**: マスクの `-3.4e38` は量子化不可 | 解像度を固定してパディングを無くせば、ViT はマスク自体が不要（全パッチが互いに見る） |
| **C-1**: float の入力が量子化されずに演算へ入ると失敗 | パッチ・位置の入力で踏みやすい。Gemma 4 の `fix_float_inputs` を流用 |
| 動的形状は不可 | 解像度（パッチ数）を固定する。アスペクト比ごとに別グラフ |
| C-11（RMSNorm の書き換え） | Gemma 4 では使ってはいけない（PLE がずれる、Gemma4 P1）。ViT でも最初は使わない |
| メモリ | 1プロセスの NPU 上限は dma-buf 約 1,710MiB。RAM 8GB のため 1.5GB のグラフ2つは同居不可（Gemma4 P6 2.6節） |

## 4. モデル選定: Gemma 4 E2B が本命

### 4.1 取得済みモデルの中身（`EdgeSLM_AndroidGemma4/work/hf/gemma-4-E2B-it-qat-mobile-transformers`）

safetensors のヘッダから集計:

| 部分 | 大きさ | 形式 |
|---|---:|---|
| 文章の層（35層） | 644.7MiB | QAT（I8/U8＋スケール） |
| 主の埋め込み／PLE の表 | 97.0MiB / 1,155.0MiB | 2bit / 4bit（CPU 側で引く） |
| **画像エンコーダ（16層）** | **144.7MiB** | **I8（出力チャネルごと）＋活性の入出力スケール（QAT）** |
| パッチの埋め込み（`input_proj`・2次元の位置の表） | 31.1MiB | BF16 |
| **射影層 `embed_vision`**（768→1536） | 4.5MiB | F32 |
| 音声エンコーダ | 約 140MiB | 本プロジェクトでは使わない |

画像エンコーダの設定（`vision_config`）: hidden 768 / 16層 / 12ヘッド（KV も 12）/ head_dim 64 / FFN 3072（GELU-tanh）/ パッチ 16px /
3×3 の平均プーリング / 2次元 RoPE（θ=100）＋2次元の位置の表 / 双方向の attention / q・k・v に RMSNorm。
1枚あたりのトークン数は 70・140・280（既定）・560・1120 から選ぶ（動画は1フレーム 70）。

| 画像トークン | パッチ数（ViT の系列長） | 例（4:3 程度） |
|---:|---:|---|
| 70 | 630 | 336×480px（21×30 パッチ） |
| 140 | 1,260 | — |
| 280 | 2,520 | 672×960px（42×60 パッチ） |

NPU に置く画像エンコーダは約 150MiB（INT8）の見込み。位置の表の引き当ては解像度を固定すれば定数になる。

### 4.2 文章側のグラフが無改造で済む理由（transformers の実装から）

`Gemma4Model.forward`（`modeling_gemma4.py` 2318〜2425行）を読んだ結果:

| 項目 | 画像トークンでの扱い | 既存グラフへの入れ方 |
|---|---|---|
| `inputs_embeds` | `embed_vision(ViT の出力)` で置き換える（masked_scatter）。**√1536 倍はしない** | 画像トークンの位置に、射影後の 1536 次元をそのまま入れる |
| PLE（`per_layer_inputs`） | 画像トークンの ID を **pad（ID 0）に置き換えて**表を引く | `ple_tok` に ID 0 の行を入れる（定数） |
| 位置 | 普通の連番（M-RoPE なし） | 既存の cos/sin のまま |
| マスク | E2B は `use_bidirectional_attention = null` → **普通の因果マスク** | 既存のマスクのまま |

つまり、端末では「画像の特徴 N 行を、1トークンずつ既存のグラフに流す」だけで済む。
ただし `project_per_layer_inputs` は `inputs_embeds` からも PLE の射影を作るため、画像の特徴の値域が文章の埋め込みと違うと、
**既存の量子化の目盛りに収まらない**おそれがある。Phase 1 で値域を確認する（要件定義書 リスク R-2）。

### 4.3 候補の比較

| 候補 | 文章側 | 日本語 | NPU 化の難度 | 判定 |
|---|---|---|---|---|
| **Gemma 4 E2B（QAT）** | **NPU で動作済み**（13〜15 tok/s） | 端末で会話済み | 低い（上記。ViT を足すだけ） | **本命** |
| Qwen2-VL-2B（LLM は Qwen2-1.5B 相当） | 近いもの（Qwen2.5-1.5B）が動作済み。ただし重みは別物で作り直し | 可 | 中（M-RoPE で位置の入力を変更） | 予備 |
| Qwen2.5-VL-3B | LLM 部分が W8 で約 3GB、1プロセスに載らない | 可 | 高 | 見送り |
| Qwen3-VL-2B | DeepStack で LLM のグラフ自体を変更 | 可 | 高 | 見送り |
| LLaVA 系の小型 VLM | 作り直し | 日本語 OCR は要確認 | 低〜中 | 予備の予備 |

## 5. 待ち時間の見込み（Gemma4 P6 の実測から）

| 画像トークン | いま（1回1トークン、約 77〜80ms） | まとめ食い 16（見込み。グラフ切替 2.3 秒込み） |
|---:|---:|---:|
| 70 | 約 5.5 秒＋文章ぶん | 約 2.7 秒 |
| 280 | 約 22 秒＋文章ぶん | 約 3.7 秒 |

これに ViT の時間（未測定）が加わる。準リアルタイム用途は 70 トークン＋まとめ食いが前提になる。
なお prefill 用と decode 用の 1.5GB のグラフは RAM 8GB では同居できないため、切り替え（約 2.3 秒）が要る。

## 6. メモリの見込み

| プロセス | 中身 | NPU（dma-buf） |
|---|---|---:|
| A（新規） | 画像エンコーダ（ViT） | 約 150〜250MiB（見込み） |
| B（既存と同じ） | Gemma 4 E2B の文章部分 | 1,467〜1,485MiB |

233MiB ＋ 1,467MiB の2プロセス同居は実測で成功している（Gemma4 P6 2.6節）。ViT がこの範囲に収まれば同じ形で動く。
