# 0. 用語集 — VLM で新しく出てくる語

[EdgeSLM_Android の用語集](../../../EdgeSLM_Android/DoC/StudyMemo/00_用語集.md) を見る。ここには画像が加わって出てくる語だけを置く。

## 0.1 画像の側

| 語 | 意味 | このプロジェクトでの値 |
|---|---|---|
| **VLM**（Vision-Language Model） | 画像と文章を入力に取り、文章を出す LLM | Gemma 4 E2B（画像・音声・文章） |
| **画像エンコーダ / ViT**（Vision Transformer） | 画像を小さな正方形（パッチ）に切り、各パッチを 1 つのトークンのように扱う Transformer | 16 層、hidden 768、12 ヘッド |
| **パッチ** | 画像を切った小さな正方形。1 パッチ＝1 行のベクトル（16×16×3＝768 個の画素値） | 16×16 ピクセル |
| **パッチの埋め込み**（patch embedder） | パッチの画素（768 個）を hidden（768）へ写す全結合＋位置の埋め込みの足し算 | `input_proj`（768→768）＋2 次元の位置の表 |
| **2 次元の位置の表** | パッチの横位置 x と縦位置 y それぞれに学習済みのベクトルがあり、足して位置を表す | 表の大きさ 2×10240×768 |
| **2 次元 RoPE** | 回転による位置の符号化を、x と y に分けてかける。head_dim の半分を x、半分を y に使う | θ＝100 |
| **双方向の attention** | 全パッチが全パッチを見る（未来を隠さない）。画像には「順番」が無いため | ViT の中だけ。文章側は因果 |
| **プーリング**（pooling） | 近くのパッチをまとめて数を減らす。Gemma 4 は 3×3 のパッチを平均して 1 つにする | 9 パッチ → 1 トークン |
| **画像トークン / soft token** | LLM に渡される、画像 1 枚分のベクトルの列。「ソフト」は、語彙の表を引いた結果ではなく連続値のベクトルという意味 | 1 枚 70 / 140 / 280（既定）/ 560 / 1120 |
| **射影層**（projector / multimodal embedder） | ViT の出力（768 次元）を LLM の埋め込みの次元（1536）へ写す層 | `embed_vision`: RMSNorm（係数なし）＋768→1536 |
| **max_soft_tokens** | HF のプロセッサに渡す「画像トークン数の上限」。パッチ数の上限はこれ×9 | Phase 1 では 70 / 140 / 280 を比べる |

## 0.2 文章側への入れ方

| 語 | 意味 |
|---|---|
| **プレースホルダ**（`<|image|>`） | chat template が文の中に置く目印。プロセッサがこれを `<|image>`＋画像トークン×N＋`<image|>` に展開する |
| **masked_scatter** | HF が、画像トークンの位置の埋め込みを画像の特徴で置き換える操作 |
| **inputs_embeds** | LLM の入口に入るベクトル列。文章の位置は語彙の表を引いたもの（×√1536）、画像の位置は射影層の出力 |
| **PLE**（Per-Layer Embeddings） | Gemma 3n / 4 の小型版の仕組み。各層に、そのトークン専用の小さな埋め込み（256 次元×35 層）を足す。表を引く部分（ple_tok）と、inputs_embeds から射影する部分がある |
| **pad の行** | 画像トークンの PLE は、語彙の表の pad（ID 0）の行を使う（画像トークンには「語彙としての ID」が無いため） |
| **因果マスク** | 各トークンが自分より前だけを見るマスク。Gemma 4 E2B は画像トークンにも因果マスクを使う（大きいモデルは画像の中だけ双方向にする設定がある） |
| **M-RoPE / DeepStack** | Qwen2.5-VL / Qwen3-VL の仕組み。前者は位置を 3 次元（時間・縦・横）で持つ、後者は ViT の複数の層の特徴を LLM の複数の層に注入する。**どちらも LLM 側のグラフを変える必要がある**（Gemma 4 E2B には無い） |

## 0.3 端末に載せるときの語

| 語 | 意味 |
|---|---|
| **固定の格子** | 端末ではグラフの形を固定する必要があるので、パッチの縦×横の数を固定する。70 トークンなら 21×30 パッチ（336×480px） |
| **レターボックス** | 縦横比の違う画像を固定の枠に収めるとき、縮小して余白を黒で埋めること（映画の上下の黒帯と同じ） |
| **native / fixed** | 本プロジェクトの前処理の名前。native＝HF の既定（縦横比に合わせて格子が変わる）、fixed＝固定の格子＋レターボックス |
| **SRQ**（Static Range Quantization） | QAT 版で、各 Linear の入力と出力を学習済みの目盛りで 8bit に丸めること。PC の HF でも再現される |
| **入口の目盛り** | 端末の文章グラフの入力（inputs_embeds・ple_tok など）を 16bit に量子化するときの scale と zero point。**文章だけで較正**してある |
| **切り詰め**（clip） | 量子化の目盛りで表せる範囲の外の値が、端の値に置き換わること |
| **まとめ食い / まとめ読み** | 1 回のグラフ実行で複数（例: 16）トークンを処理する prefill。Phase 3 までの Gemma 4 の端末グラフは 1 回 1 トークン。**Phase 5 で 16 トークン版を作った**（[10章](10_まとめ読み.md)） |
| **lmkd**（low memory killer daemon） | Android の見張り役。メモリが足りなくなると、優先度の低いアプリのプロセスから止めて場所を空ける（[9章](09_端末でつなぐ.md)） |
| **oom_score_adj** | プロセスごとの「止められやすさ」。0 ＝画面が前にあるアプリ（最後まで止められない）、50 ＝画面の無い Service、900 以上＝裏で待っているだけ。`/proc/<pid>/oom_score_adj` で読める |
| **ロード時の山** | 1.5GB のモデルを開く間だけ、ファイルをヒープに読んでから NPU 側（dma-buf）へ写すので、一時的に約 3GB 使うこと。OS に止められるのはこの瞬間 |

## 0.4 Phase 5（まとめ読み）で出てくる語

文章だけの LLM の基本語（KV キャッシュ・prefill / decode）は EdgeSLM_Android の用語集にあるが、この章で使う意味を短く書いておく。

| 語 | 意味 |
|---|---|
| **prefill（読み込み）** | プロンプトを全部読んで KV キャッシュを作る段。トークンが最初から全部分かっているので、まとめて入れられる |
| **decode（答えを作る）** | 1 つ前に出したトークンを入れて次の 1 つを出す段。前が決まるまで次が分からないので、1 つずつしか進めない |
| **KV キャッシュ / past** | それまでに読んだトークンの K（鍵）と V（値）の置き場。16 トークン版は直近 **240** トークンぶん（1 トークン版は 256） |
| **窓（window）** | 1 回の attention で見るスロットの並び。16 トークン版は past 240 ＋ この回の 16 行 ＝ 256 |
| **本物の行 / 空の行** | 16 行のうち、実際のトークンを入れた行（n 行）と、使わない残りの行（埋め込み 0、出力は捨てる）。答えを作るときは本物 1 行・空 15 行 |
| **logit_sel** | 16 行のうちどの行の答え（logits）が欲しいかを示す入力 [1,16,1]（1 つだけ 1）。最後の層のかたまりの出口で行列積の右辺に使う |
| **n_valid** | past のうち有効なスロットの数（右詰め）。マスクで開けるのはこの右端の n_valid 個と、この回の自分より前の行 |
| **KV sharing（KV の使い回し）** | Gemma 4 E2B の後ろの 20 層（15〜34）は自分の K/V を持たず、層 13（局所）・14（全体）の K/V を使う仕組み。16 トークン版はこの 2 層だけ窓全体を出力する |
| **メモリ律速** | 計算器ではなく、メモリから重みやデータが届くのを待つ時間で速さが決まる状態。スマホの NPU で LLM を動かすときは大半がこれ（1 回に約 1.55GB 読む） |
| **keep_session（開いたまま）** | job の終わりにモデルを閉じず、同じプロセスの次の job で使い回す指定。画像エンコーダの読み取りが 1.1 秒 → 0.33 秒になった |
| **一致率（HF との一致）** | 端末の答えが PC の HF（元のモデル）の答えと同じトークンを出す割合。自動判定の点数より揺れが少なく、量子化の影響を正直に表す |
| **符号検定** | 2 つの条件で 1 問ずつの正誤が入れ替わった数（×→○ と ○→×）だけを使い、偏りが偶然で出る確率を出す検定。11 対 2 なら約 2% |
