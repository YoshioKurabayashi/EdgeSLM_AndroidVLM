## 7.1 なぜ HF のコードをそのまま書き出さないのか

HF の `Gemma4VisionModel` は、**どんな縦横比の画像でも受け付ける**ように書かれている。

- パッチの位置 (x, y) を入力で受け取り、位置の表を**引く**（Embedding ＝ Gather）
- 2 次元 RoPE の cos/sin を位置から**毎回計算**する
- パディング（位置 −1）を見分けて、attention のマスクとプーリングで除く
- プーリングは位置から「どの 3×3 に属するか」を計算し、one_hot の行列を作って掛ける

端末では格子を固定する（[3 章](03_NPUに載せるための設計.md)）。すると上の「毎回計算していたもの」は**全部定数**になる。
定数にできるものを定数にすると、グラフから Gather・マスク・動的な形が消え、v68 の制約（C-1・C-9・C-10）に当たる場所が減る。

> EdgeSLM_Android の教訓「**数学的に同じ答えを出す別の形に変形し、ハードに都合のよい形にする**」（StudyMemo 5 章）の実践。

## 7.2 書き換え 1: 位置を定数にする

70 トークンの格子は 21×30 パッチ。パッチ n の位置は x = n mod 30、y = n div 30 で決まっている。

$$
\text{POS}[n] = \text{table}_x[\,n \bmod 30\,] + \text{table}_y[\,\lfloor n/30 \rfloor\,] \quad (630 \times 768 \text{ の定数})
$$

cos/sin も同じく [630, 64] の定数表。**入力は画素だけ**になる。

## 7.3 書き換え 2: プーリングを reshape と平均で書く

HF は「630 × 70 の重み行列（1/9 が 9 個ずつ並ぶ）× 隠れ状態」で平均を取る。これを書き出すと、630×70 の定数行列が
MatMul の重みとしてグラフに入り、量子化の工程で「QAT でない重み」として扱う手間が増える。

代わりに、並びを利用する。パッチ n = y·30 + x なので:

```
[630, 768] → [21, 10, 3, 768] → 3 の軸で平均 → [21, 10, 768]      （横の 3 つ）
           → [7, 3, 10, 768]  → 3 の軸で平均 → [7, 10, 768]       （縦の 3 つ）
           → [70, 768]                                           （出力 m = ky·10 + kx）
```

出力の並び（ky·10 + kx）は HF の「kx + (max_x / 3)·ky」と同じ。numpy で両方を計算して差が 2e-16（丸めだけ）であることを確かめた。
テンソルは 4 次元までに収めた（NPU は高い次元が苦手なことがある）。

## 7.4 書き換え 3: ×√768 を消す（RMSNorm の性質を使う）

HF はプーリングの後に ×√768（≒27.7）を掛け、すぐ射影層の RMSNorm（重みなし）に入れる。RMSNorm は「大きさで割る」ので、
前に掛けた定数はほぼ消える:

$$
\mathrm{RMSNorm}(c\,x;\ \varepsilon) = \frac{c\,x}{\sqrt{c^2\,\overline{x^2} + \varepsilon}} = \frac{x}{\sqrt{\overline{x^2} + \varepsilon / c^2}} = \mathrm{RMSNorm}(x;\ \varepsilon / c^2)
$$

$c^2 = 768$ なので、**掛け算を消して eps を 1/768 にすれば同じ計算**。

なぜ消すか:

- **演算が 1 つ減り、量子化（Q/DQ）も 1 組減る。** 量子化のたびに小さな丸めが入るので、意味の無い演算は無い方がよい
- HF のコメントに「×√768 で fp16 の範囲（65504）を超えうる」とある。NPU のどこかが fp16 で計算されても溢れにくい

**精度が上がるわけではない**ことに注意。最初は「値を 27.7 倍に広げないので 16bit の目盛りが粗くならない」と書いたが、
レビューで誤りと指摘された。テンソル全体で 1 つの目盛り（per-tensor）なら、x を c 倍すると目盛りの幅も c 倍になり、
**値に対する相対的な細かさは同じ**。目盛りが粗くなるのは「一部の値だけが巨大で、他の値の範囲が狭い」ときで、
全体を定数倍することとは別の話（EdgeSLM_Android StudyMemo 2・3 章）。

check で、消した形と消さない形が 1e-6 以下で一致することを確かめる。

## 7.5 書き換えなかったもの

| もの | 理由 |
|---|---|
| RMSNorm の x² の書き換え（C-11） | Gemma4 で「eps を 1e-12 にするため PLE が 17.8% ずれた」ので使わない。形は Gemma4 と同じ（QAIRT が RmsNorm に融合する形） |
| 注意のスコアの大きさ（630×630×12） | まず素直な形で変換を試す。VTCM（4MB）に入らない分は HTP が分割する。遅ければヘッドごとに分ける |
| 2·(p − 0.5) | グラフの中に残す。入力を最初に使う演算が Sub になり、C-1（入力が Reshape などに直接入ると量子化されない）を避けられる |

## 7.6 確かめ方（6 章と同じ考え方）

1. HF の正解を取る（`capture_vit`。SRQ あり・なし、途中の値も）
2. 自前の配線を **SRQ なし**で HF と比べる（1e-4 以下、理想 1e-5）。ずれたら途中の値で「どの層から」を探す。
   足し算の順序の差なら層ごとに 1e-6 の桁で滑らかに増え、配線の誤りならある層で急に 1e-2 以上に跳ぶ
3. ONNX に書き出して ORT CPU で動かし、自前の配線と比べる（同じ目安）
4. SRQ ありの比較は記録だけ（境目で転ぶ分がある）

正解（HF）は CPU で取る。GPU で取ると、GPU の行列積・attention の足し算の順序の差（1e-5 前後）が混ざり、
配線の誤りと区別しにくくなる。

## 7.8 ★SRQ（8bit の丸め）への敏感さ — 画像エンコーダは文章側よりずっと揺れる

一番大きな発見は、配線の正しさではなく**揺れの大きさ**だった。

| 比較 | 出力の相対 L2 の平均 | cos 最小 |
|---|---:|---:|
| 自前 ↔ HF（SRQ なし） | 0.0000012 | 0.999999999998 |
| **自前 ↔ HF（SRQ あり）** | **0.32** | **0.84** |
| HF の SRQ あり ↔ なし | 0.52 | 0.86 |

SRQ なしでは 6 桁一致する同じ計算が、SRQ を掛けると 3 割も離れる。理由は 6.3 節と同じ（微小な差が 8bit の境目で 1 目盛り転び、層を追って広がる）だが、

- QAT の活性の目盛りが粗い（スケール 0.015〜0.71。1 目盛りが値に対して大きい）
- SRQ を掛けるだけで、層 0 で既に 1〜2 割動く（HF の SRQ あり ↔ なし）

ため、文章側（1 位の一致 77〜89%）よりずっと強く出る。

### ここから言えること

> **「端末の特徴が HF と cos 0.99 で一致すること」を合格の条件にしてはいけない。** 正しく作っても 0.85 前後までずれうる。

代わりに:

1. **算術の誤差は SRQ なしの版で見る**（揺れの源を止める。6.4 節の「小さな効果を測るときは、大きな揺れの源を先に止める」と同じ）
2. **SRQ ありの版は答えの品質で判定する**（Phase 1 の「全体の点と入れ替わりの偏り」）
3. その前に、**特徴が 3 割変わっても答えが保たれるか**を PC で確かめる（自前の配線の特徴で 126 問を解く）。
   保たれなければ、「揺れにくい作り方」（SRQ の目盛りの境目を避ける工夫など）を考える必要がある

### ★確かめた（2026-09-28）: 特徴が揺れても答えは保たれる

自前の配線の特徴で 126 問を解いた。

| 画像エンコーダ | HF の特徴との cos（中央値） | 点 |

## 7.9 ★量子化してみる（2026-09-28、[記録](../../results/P2_20260928_vit_quant.md)）— 新しい誤差は「すでにある揺れ」と比べる

文章側（Gemma4）と同じ道具・同じ順序で量子化した: 活性は 16bit（テンソル全体で 1 つの目盛り）、重みは 8bit（出力チャネルごと）、
活性×活性の行列積の右辺（K と V）は 8bit（C-8）。版は 2 つ作った。

| 版 | 中身 | 何に使うか |
|---|---|---|
| SRQ あり | QAT の 8bit の丸めを、Linear の入出力に Q/DQ として入れる | 本来のモデル。答えの品質で判定 |
| SRQ なし | 丸めを入れない（活性は 16bit のまま） | 揺れが無いので、量子化の算術の誤差だけが見える |

### 重みの誤差はほぼ 0

QAT のモデルは、重みを「8bit の整数 × スケール」の形で持っている。その整数とスケールを**そのまま**書き込むので、112 本の重みは
**量子化の誤差が 0**（完全一致を検査している）。自分で 8bit にしたのは、QAT でない 2 本（パッチの埋め込み・射影層）だけで、誤差は約 1%。

> QAT 済みのモデルを量子化するときは「較正で目盛りを決め直す」のではなく「学習で決まった目盛りを写す」。決め直すと、せっかく
> 学習で合わせた値からずれる。

### 結果を「すでにある揺れ」と並べる

| 比較 | cos（最小〜中央値） |
|---|---|
| SRQ なしの版 ↔ HF（SRQ なし）＝ **量子化の算術の誤差** | **0.997〜0.999** |
| 自前の float・SRQ あり ↔ HF（SRQ あり）＝ 量子化する前からある揺れ（7.8） | 0.84〜 |
| SRQ ありの版 ↔ HF（SRQ あり） | 0.81〜0.92 |

量子化で増えた誤差（cos で 0.003 ほど）は、SRQ の揺れ（0.1〜0.2）に比べて 1 桁以上小さい。SRQ ありの版の cos が低いのは量子化のせいではなく、
量子化する前から HF とそれだけ離れていた。

ここでの考え方:

- **新しく入れた誤差の大きさは、「すでにある、避けられない揺れ」と比べて判断する。** 揺れより十分小さければ、答えの品質を変える力は無い
- 比べるときは揺れの源を止めた版（SRQ なし）で測る。止めずに測ると、量子化の誤差が揺れに埋もれて見えない（6.4 節と同じ）
- 相対 L2 3.7% の内訳（8bit の K・V か、作り直した 2 本の重みか）は測らなかった。合格しているものを細かく分けるより、
  端末で大きな差が出たときにこの順で疑う、と記録しておく方が安い

### 大きさで重みの bit 数を確かめる

150MiB ＝ 重み 1.5 億 × 1 バイト。float の ONNX は 587MiB（× 4 バイト）。**ファイルの大きさを「パラメータ数 × バイト数」で見積もって合うか**を
見るだけで、「8bit のつもりが 16bit や 32bit のまま残っている」誤りは見つけられる。

量子化の段で C-1（float を残さない）と C-8（活性×活性の右辺を 8bit）を済ませてあったので、変換で新しくつまずく所は無かった。

### 生成ログの「DDR bandwidth summary」を読む

context binary を作るときに、QAIRT は「1 回動かすと DDR（普通のメモリ）と何バイトやり取りするか」の見積もりをログに出す。

| | 書き出し（spill） | 読み出しの合計 |
|---|---:|---:|
| 画像エンコーダ（630 トークンを 1 回で） | 約 1GB | 約 1.2GB |
| 文章側のかたまり（1 トークン） | 0.6MB | 0.24GB（ほぼ重みだけ） |

NPU には VTCM という小さく速いメモリ（v68 は 4MB）があり、計算の途中の値はなるべくそこに置く。置けない分は DDR に書き出して、
使うときに読み戻す（spill / fill）。

- **文章側は 1 回 1 トークン**なので、途中の値は数 KB〜数百 KB。VTCM に収まり、DDR とのやり取りは「重みを読む」だけ
- **画像エンコーダは 630 トークンを一度に**通すので、attention の点数（12 頭 × 630 × 630）だけで 1 層 9.5MB。VTCM に入らず、重みの十数倍の量を出し入れする

同じ「16bit の活性・8bit の重み」の Transformer でも、**一度に通すトークン数で、NPU の上での振る舞い（何が時間を食うか）がまるで変わる**。
文章側では「重みを読む速さ」が時間を決めていたが、画像エンコーダでは「途中の値の出し入れ」が効いてくるかもしれない。
端末で時間を測ったとき（2-4）、この数字と並べて読む。

> ログは「成功／失敗」だけ見て閉じがちだが、生成ログの見積もり（spill の量）や メタデータ（重み・作業データの大きさ）は、
> 端末で測る前に「どこが重そうか」「メモリはどれくらいか」の見当をつける材料になる。
