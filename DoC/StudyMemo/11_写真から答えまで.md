## 11.1 登場人物 — 2 つのプロセスと 2 つのモデル

```
┌──────────── 主プロセス（org.edgeslm.vlm）──────────────┐     ┌──── 別プロセス（:probe）─────────┐
│ VlmActivity（画面）                                    │     │ RunnerService2                   │
│   ・写真の読み込み・EXIF の向き（Kotlin）              │ job │   ・画像エンコーダ（ViT）         │
│   ・前処理（C++、nativeVlmPrep）                       │ ──▶ │     152MiB、NPU、開いたまま       │
│   ・トークナイザ（Kotlin、Gemma4Tokenizer）            │ ◀── │   ・結果はファイル（特徴 70×1536）│
│   ・文章側（C++、nativeRunJob → generate_kv）          │ 結果 └──────────────────────────────────┘
│       Gemma 4 E2B 16 トークン版 1,467MiB、NPU、開いたまま│
└────────────────────────────────────────────────────────┘
```

- **NPU のメモリはプロセスごとに約 1,710MiB まで**（[3.3 節](03_NPUに載せるための設計.md)）。文章側 1,467MiB と画像エンコーダ 152MiB を別々のプロセスに置く
- 2 つとも「開いたまま」にしておく。文章側は画面を開いたときに 1 回（2.3 秒）、画像エンコーダはその直後に「開くだけ」の job で（[10.9 節](10_まとめ読み.md)）
- CPU で動くのは、写真の復号・前処理・トークナイザ・埋め込みの表を引くところ・KV キャッシュの出し入れ・答えの選択（argmax）だけ。
  **行列の計算は全部 NPU**（ログの `strict=true` ＝ CPU への逃げ道なし）

## 11.6 答えを止める 3 つの条件

| 条件 | 中身 | 画面 |
|---|---|---|
| 終わりの印 | `stop_ids` = 106（`<turn|>`）・1（`<eos>`）・50 のどれかが出た | 普通に終わる |
| 上限 | `max_new` = 96 個に達した | 答えの最後に「…（長いので途中まで）」（Phase 5） |
| 停止ボタン | 利用者が押した（C++ の cancel フラグ） | それまでの答えをそのまま表示（何も出ていなければ「（停止しました）」） |

126 問の評価（上限 64）では、答えの約 3 割（40〜44 問）が上限で切れていた（デモの上限は 96）。Gemma 4 E2B は丁寧に長く書く癖がある。
「簡潔に」と system 文で頼んでも短くなりきらない。上限を伸ばすと 1 トークン 80ms ずつ待ちが延びる。

## 11.7 いま時間を使っているのはどこか

1 枚目の 1 問（写真を撮り終えてから答えが出終わるまで、利用者の操作時間を除く）:

| 段 | 時間 | 割合 |
|---|---:|---:|
| 写真の読み込み・前処理・画像エンコーダ | 0.46 秒 | 5% |
| まとめ読み（最初の文字まで） | 0.93 秒 | 10% |
| **答えを 1 トークンずつ（残り 95 個）** | **7.74 秒** | **85%** |

Phase 3 では「最初の文字まで」が 8 秒で一番重かったが、**今は答えを作る段が 9 割近く**を占める。次に速くするなら:

| 手 | 効き目の見込み | 難しさ |
|---|---|---|
| 答えを短くする（system 文・上限） | 長さに比例して速くなる | 易しい。品質との兼ね合い |
| 答えを作るときだけ 1 トークン版に持ち替える | 1 トークン 81 → 77ms（5%） | RAM が足りず 2 本持てない（10.3 節） |
| 1 回で数トークンずつ当てにいく（投機的デコード） | 当たれば 2〜3 倍 | 小さい下書きモデルがもう 1 つ要る。v68 では試していない |

## 11.8 まとめ

1. **2 つのプロセス・2 つのモデル**（文章側 1,467MiB と画像エンコーダ 152MiB、どちらも NPU・開いたまま）。CPU は前処理と表引きと出し入れだけ
