# 11. 写真から答えまでを端から端まで — いまの端末の VLM を 1 本の流れで追う

[← 目次へ](../StudyMemo.md) | [← 前: 10. まとめ読み](10_まとめ読み.md)

1〜10 章は部品ごとに見てきた。この章では **Phase 5 を終えた今の形**で、写真 1 枚が日本語の答えになるまでを、
**形（行列の大きさ）・場所（どのプロセスのどの部品か）・時間（実測）**を並べて一度に追う。
数字は 2026-09-30 の「後」の動画のログ（`results/P3_device_vlm/demo/vlm_demo_20260930_093512_after_log.txt`）と、126 問の評価から。
全体の構成の正式な説明は [システム設計書](../システム設計書.md)。

---

## 11.1 登場人物 — 2 つのプロセスと 2 つのモデル

```
┌──────────── 主プロセス（org.edgeslm.vlm）──────────────┐     ┌──── 別プロセス（:probe）─────────┐
│ VlmActivity（画面）                                    │     │ RunnerService2                   │
│   ・写真の読み込み・EXIF の向き（Kotlin）              │ job │   ・画像エンコーダ（ViT）         │
│   ・前処理（C++、nativeVlmPrep）                       │ ──▶ │     152MiB、NPU、開いたまま       │
│   ・トークナイザ（Kotlin、Gemma4Tokenizer）            │ ◀── │   ・結果はファイル（特徴 70×1536）│
│   ・文章側（C++、nativeRunJob → generate_kv）          │ 結果 └──────────────────────────────────┘
│       Gemma 4 E2B 16 トークン版 1,467MiB、NPU、開いたまま│
└────────────────────────────────────────────────────────┘
```

- **NPU のメモリはプロセスごとに約 1,710MiB まで**（[3.3 節](03_NPUに載せるための設計.md)）。文章側 1,467MiB と画像エンコーダ 152MiB を別々のプロセスに置く
- 2 つとも「開いたまま」にしておく。文章側は画面を開いたときに 1 回（2.3 秒）、画像エンコーダはその直後に「開くだけ」の job で（[10.9 節](10_まとめ読み.md)）
- CPU で動くのは、写真の復号・前処理・トークナイザ・埋め込みの表を引くところ・KV キャッシュの出し入れ・答えの選択（argmax）だけ。
  **行列の計算は全部 NPU**（ログの `strict=true` ＝ CPU への逃げ道なし）

## 11.2 時間の流れ（実測、1 枚目の写真）

| 時刻 | 何が起きたか | かかった時間 |
|---|---|---|
| 09:35:15.5 | 画面が開く → 文章側のモデルを開き始める | — |
| 09:35:17.8 | `vlm text ready: load_ms=2323` → すぐ画像エンコーダを「開くだけ」の job | **2.3 秒** |
| （利用者が写真を撮る） | カメラアプリ（Sony のカメラ）で撮影して戻る | — |
| 09:36:05.3 | 写真の読み込み: 4032×3024 の JPEG を 1/4 で復号 → EXIF の向きで回して 756×1008 | 116ms |
| 09:36:05.3 | 前処理（C++）: 336×480 に収めて黒で余白 → 630 パッチ | 17ms |
| 09:36:05.7 | 画像エンコーダ（別プロセス、開いたまま）→ 特徴 70×1536 | **328ms**（NPU 258ms） |
| （利用者が質問を選ぶ） | 「この画像を説明してください。」 | — |
| 09:36:09.6 | プロンプトを作る（107 トークン） → まとめ読み 7 回 → 答えの 1 つ目 | **0.93 秒** |
| 〜09:36:18.3 | 答えを 1 トークンずつ 96 個（上限） | 中央値 81.5ms/トークン、合計 8.67 秒 |
| 同上 | 上限で切れたので、答えの最後に「…（長いので途中まで）」 | — |

同じ流れを Phase 3（1 トークン版・画像エンコーダを毎回開く）と比べる:

| | Phase 3（前の動画） | Phase 5（後の動画） |
|---|---:|---:|
| 写真の読み取り（画像エンコーダ） | 1.0〜1.2 秒 | **0.33 秒** |
| 質問してから最初の文字まで | 7.8〜8.4 秒 | **0.78〜0.93 秒** |
| 答えの 1 トークン（中央値） | 64〜76ms | 77.5〜81.5ms |

## 11.3 形の変化 — 写真が 107 個のベクトルになり、1 つの語になるまで

| # | 段 | 形 | どこで |
|---|---|---|---|
| 0 | カメラの JPEG | 4032×3024（EXIF で 90° 回転の印） | ストレージ |
| 1 | 復号（1/4 に間引き）＋向きを直す | 756×1008×3（RGB） | Kotlin |
| 2 | 縦横比を保って 336×480 に収める（PIL の BICUBIC を C++ で再現）、余白は黒 | 336×480×3 | C++ |
| 3 | 16×16 のパッチに切り、÷255 | **630 × 768**（21×30 パッチ） | C++ |
| 4 | 画像エンコーダ: パッチの埋め込み → ViT 16 層 → 3×3 平均 → ×√768 → 射影層 | **70 × 1536** | NPU（:probe） |
| 5 | プロンプトの ID を作る（下の 11.4） | 107 個の ID（うち 70 個は画像トークン 258880） | Kotlin |
| 6 | 1 行ずつ埋め込みを作る: 文章の ID は 2bit の表を引いて ×√1536、画像トークンの位置は **4 の特徴の 1 行をそのまま**。PLE は表を引く（画像の位置は pad の行） | inputs_embeds 107×1536、ple_tok 107×35×256 | C++ |
| 7 | 16 行ずつ文章側のグラフへ（7 回）。各回で KV キャッシュに 16 行ずつ足す | 1 回 [1,16,1536] | NPU（主） |
| 8 | 最後の回の「最後の本物の行」だけ出力層へ → 262,144 語の点数 | logits [1,1,262144] | NPU |
| 9 | 一番点の高い語を選ぶ（argmax） | 1 個の ID | C++ |
| 10 | ID を文字にする（バイト列を少しずつ UTF-8 に） | 文字 | Kotlin |

**画像の特徴は「語の埋め込みの代わりに置く 70 行」にすぎない**（[1 章](01_VLMの構造.md)）。文章側のグラフは、画像が入っているかどうかを知らない。

## 11.4 プロンプトの中身（実際の ID）

ログの `vlm prompt first=true n=107 ids=…` を読み解く（system 文は「添付の画像を見て、質問に日本語で簡潔に答えてください。」）。

| 位置 | ID | 意味 |
|---|---|---|
| 0 | 2 | `<bos>`（文の始まり） |
| 1〜3 | 105, 9731, 107 | `<|turn>` `system` `\n` |
| 4〜19 | 213371, 236945, 32613, … 236924 | system 文（16 トークン） |
| 20〜24 | 106, 107, 105, 2364, 107 | `<turn|>` `\n` `<|turn>` `user` `\n` |
| 25 | 255999 | `<|image>`（画像の始まり） |
| 26〜95 | 258880 × 70 | **画像トークン**（ここに画像の特徴が入る） |
| 96 | 258882 | `<image|>`（画像の終わり） |
| 97〜101 | 8978, 232468, 34084, 49391, 236924 | 質問「この画像を説明してください。」 |
| 102〜106 | 106, 107, 105, 4368, 107 | `<turn|>` `\n` `<|turn>` `model` `\n`（ここから答え） |

- 画像トークンの ID（258880）は**目印**。埋め込みの表は引かず、画像の特徴の行に差し替える（PLE だけは pad の行を引く）
- 2 問目以降（同じ写真への追加の質問）は、`<turn|>\n<|turn>user\n{質問}<turn|>\n<|turn>model\n` の**差分だけ**（約 16 トークン）。
  前の KV キャッシュと位置を持ち越すので、読むのは 1〜2 回で済む（2 問目の最初の文字: 前の動画 1.4 秒 → 後の動画 0.22〜0.24 秒。差分 15 トークンを 1 回で読む）

## 11.5 KV キャッシュの一生

| 時点 | past（覚えている数、最大 240） | 位置（abs_pos） |
|---|---:|---:|
| 写真を読んだ直後 | 0（新しい写真なので空にする） | 0 |
| まとめ読み 7 回の後 | 107 | 107 |
| 答え 96 個の後 | 202 | 202（ログの `abs_pos=202`） |
| 2 問目の差分 16 個の後 | 218 | 218 |
| 2 問目の答えが 22 個を超えたら | 240 で頭打ち（古い方から押し出される） | 増え続ける |

**押し出されるのは古い方＝system 文と画像の側**。画像が押し出された後に質問しても答えられないので、端末は
「past が満杯になったら、次の質問は写真から作り直す」（`abs_pos` > 240 で `chatStarted = false`）。
窓を大きくする（L512）には、グラフをもう 1 本作る必要がある（280 トークンの画像を使うときの課題）。

## 11.6 答えを止める 3 つの条件

| 条件 | 中身 | 画面 |
|---|---|---|
| 終わりの印 | `stop_ids` = 106（`<turn|>`）・1（`<eos>`）・50 のどれかが出た | 普通に終わる |
| 上限 | `max_new` = 96 個に達した | 答えの最後に「…（長いので途中まで）」（Phase 5） |
| 停止ボタン | 利用者が押した（C++ の cancel フラグ） | それまでの答えをそのまま表示（何も出ていなければ「（停止しました）」） |

126 問の評価（上限 64）では、答えの約 3 割（40〜44 問）が上限で切れていた（デモの上限は 96）。Gemma 4 E2B は丁寧に長く書く癖がある。
「簡潔に」と system 文で頼んでも短くなりきらない。上限を伸ばすと 1 トークン 80ms ずつ待ちが延びる。

## 11.7 いま時間を使っているのはどこか

1 枚目の 1 問（写真を撮り終えてから答えが出終わるまで、利用者の操作時間を除く）:

| 段 | 時間 | 割合 |
|---|---:|---:|
| 写真の読み込み・前処理・画像エンコーダ | 0.46 秒 | 5% |
| まとめ読み（最初の文字まで） | 0.93 秒 | 10% |
| **答えを 1 トークンずつ（残り 95 個）** | **7.74 秒** | **85%** |

Phase 3 では「最初の文字まで」が 8 秒で一番重かったが、**今は答えを作る段が 9 割近く**を占める。次に速くするなら:

| 手 | 効き目の見込み | 難しさ |
|---|---|---|
| 答えを短くする（system 文・上限） | 長さに比例して速くなる | 易しい。品質との兼ね合い |
| 答えを作るときだけ 1 トークン版に持ち替える | 1 トークン 81 → 77ms（5%） | RAM が足りず 2 本持てない（10.3 節） |
| 1 回で数トークンずつ当てにいく（投機的デコード） | 当たれば 2〜3 倍 | 小さい下書きモデルがもう 1 つ要る。v68 では試していない |

## 11.8 まとめ

1. **2 つのプロセス・2 つのモデル**（文章側 1,467MiB と画像エンコーダ 152MiB、どちらも NPU・開いたまま）。CPU は前処理と表引きと出し入れだけ
2. 写真 4032×3024 → 756×1008 → 336×480 → **630 パッチ → 70 トークン** → プロンプト 107 トークン → 7 回のまとめ読み → 答え
3. **画像トークンは「表を引かない 70 行」**。文章側のグラフは画像を知らない（PLE は pad の行）
4. いまは **最初の文字 0.9 秒・写真の読み取り 0.3 秒**。時間の 85% は答えを 1 つずつ作る段
5. 覚えていられるのは 240 トークン。あふれたら写真から作り直す
