# 8. 端末でだけ壊れる — 小さすぎるスケールと、途中の値での切り分け（2026-09-29）

[← 目次へ](../StudyMemo.md) | [← 前: 7. 画像エンコーダを書き直す](07_画像エンコーダを書き直す.md) | [次: 9. 端末でつなぐ →](09_端末でつなぐ.md)

[記録](../../results/P2_20260929_vit_device.md) の 7 節。Phase 2-4 で、画像エンコーダは端末の NPU で**エラーなく全部動いた**のに、
**出力がでたらめ**だった。PC で量子化を真似た値（QDQ）は HF と cos 0.997 で合っていたので、「端末でだけ壊れる」型である。

---

## 8.1 何が見えたか

- CPU に逃げずに全部 NPU で動いた（strict=true）。時間もメモリも普通
- ところが出力は PC とも HF とも無関係（cos 0.05）。しかも**どの画像でも、どのトークンでもほぼ同じ値**（cos 0.999〜1.0）

「全部同じ値」は強い手がかりに見える。候補を 3 つ挙げた:

1. 630 トークンの 4 次元のテンソルの軸の扱い（文章側はトークン 1 つなので、取り違えても長さ 1 の軸で隠れる）
2. 層 5 から現れる巨大な活性（最大 2,158）と 16bit の計算
3. 長さ 630 の softmax

**3 つとも外れだった。** 原因は一番最初の段（パッチの埋め込み）にあった。

## 8.2 切り分けの考え方: 途中の値をグラフの出力に足す

端末の中は context binary（中身の見えない塊）なので、途中の値は取れない。そこで**途中の値もグラフの出力にした版**を作る。

- 比べる相手は HF ではなく、**同じグラフの PC の QDQ**（量子化だけを真似たもの）。こうすると量子化の誤差は差し引かれ、
  **端末だけの差**が見える（6 章の「同じ形どうしで比べる」と同じ）
- まず**小さい版（2 層だけ）**を作る。変換が 89 秒で済む（16 層は 56 分）。原因が前の方にあるなら、小さい版で見つかる
- 途中の値ごとに「端末 ↔ PC の QDQ の相対 L2」を並べ、**最初に大きくずれる所**を探す

結果は、最初の出力（パッチの埋め込み）で既に相対 L2 21.8。層も softmax も関係なかった。

## 8.3 壊れ方を「形」で読む

パッチの埋め込みの端末の値を細かく見ると:

| 見たもの | 分かったこと |
|---|---|
| 29% の値が出力の範囲の端（±68.45）に張り付いている | どこかで値が溢れている |
| 張り付いた値の符号は、本当の値の符号と無関係（一致 51%） | 「大きすぎて切られた」のではなく、**でたらめな値**が出ている |
| 張り付くかどうかは**チャネルで決まる**（222 本はほぼ全トークン、545 本はほぼ無し） | トークン（画像の場所）ではなく、**チャネルごとの何か**が原因 |
| 張り付かないチャネルは PC とぴったり一致（倍率 1.000） | 計算の仕組みそのものは正しい |

「チャネルごとの何か」で、量子化の器にあるものは**重みのスケール（出力チャネルごと）**。並べてみると、
**スケール 4.0e-6 未満のチャネルは全部壊れ、4.1e-6 以上は全部正常**。境目がきれいに分かれた。

> 壊れ方の「形」（範囲の端に張り付く・符号がでたらめ・チャネルで決まる）を 1 つずつ確かめると、候補が一気に絞れる。
> 「全部同じ値」は結果の見え方であって、原因の場所を指していなかった。

## 8.4 なぜスケールが小さいと壊れるのか

量子化した行列積を NPU は整数で計算する:

```
y の整数 = 丸め( M × Σ (x の整数 − 零点) × (重みの整数) ) ＋ 出力の零点
M = 入力のスケール × 重みのスケール ÷ 出力のスケール
```

M は小数だが、NPU は M も「整数の倍率 × 2 の負のべき」の固定小数点で持つ。**M が小さすぎると表せる範囲を外れ**、でたらめな値になる
（今回の境目は M ≒ 6e-8 ≒ 2⁻²⁴ の見当）。

パッチの埋め込みの重みには、**ほぼ 0 のチャネルが 222 本**あった（max|w| 2e-8〜5e-4、ふつうは 0.03 前後）。学習で使われなくなった
チャネルとみられる。「max|w|/127 をスケールに」という素直な作り方だと、そのチャネルのスケールも極端に小さくなる。

**PC の ORT では壊れない**。ORT の QDQ は「整数に丸めて float に戻し、float で計算する」ので、M を固定小数点で持つ段が無い。
つまり **PC の QDQ は「丸め」は真似るが、「NPU の整数の計算の限界」は真似ない**。

## 8.5 直し方と、見張り

- スケールに下限を付ける（そのテンソルの最大のスケールの 1/64）。ほぼ 0 の重みは、整数が 0〜十数になるだけで値はほとんど変わらない
  （出力の相対 L2 0.266% → 0.268%）
- 量子化の段で「重みのスケールの最小/最大」を検査する（C-14）。QAT の重みは最小/最大 0.09 以上で問題ない

## 8.5.1 ★確かめた（2026-09-29）

| 途中の値 | 端末 ↔ PC の QDQ（直す前 → 後） |
|---|---|
| パッチの埋め込み | 相対 L2 21.8 → **0.008** |
| 層 0 / 層 1 | 13.2 / 9.9 → **0.024 / 0.021** |
| 最終出力（16 層、16 枚） | 2.2 → **0.074**（HF との cos 最小 0.991） |

下限を付けるだけで直った。残る端末だけの差（層 0・1 で 2% 前後、最後で 7% 前後）は、630 トークンを一度に扱うことによる
端末の計算の差とみられる（EdgeSLM_Android でも「長さが長いほど端末だけの誤差が増える」記録がある）。
答えの品質が保たれるかは 2-5 で確かめる。

**確かめた（2-5）**: 端末の NPU で作った特徴で 126 問を解くと 45/123（HF の画像エンコーダ 42/123、量子化前の自前 45/123）。端末だけの誤差 7% は答えの品質を変えなかった。

## 8.6 ここから言えること

1. **「動いた（エラーなし）」と「正しい値が出た」は別**。strict=true・時間も普通、でも値はでたらめ、はあり得る。必ず値を比べる
2. **端末だけの差は「同じグラフの PC の QDQ」と比べる**。HF と比べると量子化の誤差と混ざる
3. **途中の値を出力に足した版を、小さい版から作る**。変換が速いので、原因が前の方ならすぐ見つかる
4. **壊れ方の形を読む**（張り付き・符号・チャネルかトークンか）。原因の見当（巨大な活性など）を先に決めつけると外す
5. **「ほぼ 0 の重み」は無害に見えて、量子化の器では害になる**。float から量子化するときはスケールに下限を付ける
