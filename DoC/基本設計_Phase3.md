| | |
|---|---|
| 作成 | 2026-09-29 |
| 前提 | Phase 2（70 トークン・横長）: 画像エンコーダは端末の NPU で 1 枚 159〜195ms・152MiB、文章側（1,467MiB）と別プロセスで同居でき、端末の特徴で答えの品質 45/123（基準 42） |

## 1. 目標

| # | 問い | 合格の目安 |
|---|---|---|
| Q13 | 端末の中だけで「写真 → 日本語の答え」が出るか | カメラで撮った写真に、機内モードのまま答える（全部 NPU） |
| Q14 | 端末の前処理は PC と同じ値か | 同じ RGB から作った pixel_values が PC（PIL）とビット一致（C++ で PIL の BICUBIC を再現） |
| Q15 | 端末だけで 126 問を解いて、品質が PC と同じか | 端末の画像エンコーダ ＋ 端末の文章側（1 トークンずつ）で 126 問。PC（42〜49/123）と同等、入れ替わりに偏りなし |
| Q16 | 待ち時間 | 最初の文字まで 10 秒前後の見込み（画像 1 秒 ＋ 文章 約 117 トークン × 66ms） |

## 2. 全体の形

```
[カメラ] → JPEG（MediaStore） → [VlmActivity（主プロセス）]
   ① 読み込み・EXIF の向き（Kotlin、android.media.ExifInterface）→ RGB のバイト列
   ② 前処理（C++、nativeVlmPrep）: 縮小（PIL の BICUBIC を再現）→ 黒で余白 → 16×16 のパッチ → pixel_values [630,768] float32
   ③ 画像エンコーダ（別プロセス :probe の RunnerService2 に job を渡す。152MiB を開いて 1 回動かして閉じる）→ 特徴 [70,1536]
   ④ 文章側（主プロセスで開いたまま、1,467MiB）: generate_kv に特徴を渡す。画像の位置は埋め込み表を引かず特徴をそのまま入れ、
      PLE は pad（0）の行を引く（Phase 1 で HF とビット一致を確かめた入れ方）
   ⑤ 1 トークンずつ表示。答えの下に「画像 0.9 秒（NPU 160ms）・最初の文字まで 9.1 秒・15 tok/s・全部 NPU」
```

- **画像エンコーダを別プロセスにする理由**: NPU の上限はプロセスごと約 1,710MiB。文章側 1,467MiB ＋ 画像 152MiB ＝ 1,619MiB は
  1 プロセスでも入る計算だが余裕が少ない。別プロセスでの同居は 2-4 で確かめ済み（coexist）。毎回開き直すので +0.7 秒かかるが、
  まず確実に動く形にする（常駐させる改良は Phase 5）
- **既存の仕組みを使う**: 画像エンコーダは RunnerService2（Gemma4 のアプリにあった「別プロセスの job の入口」）で、`infer` の job を
  そのまま流す。文章側は ChatActivity と同じく主プロセスで `nativeCreate` → `nativeRunJob(generate_kv)`
- **プロンプト**: Phase 1 と同じ system 文（「画像についての質問に、日本語で簡潔に答えてください。」）と書式
  `<bos><|turn>system\n{system}<turn|>\n<|turn>user\n` ＋ `<|image>`(255999) ＋ 画像トークン(258880)×70 ＋ `<image|>`(258882) ＋ `{質問}<turn|>\n<|turn>model\n`。
  HF のプロセッサは `<|image|>` を「始まり＋画像トークン×N＋終わり」に置き換える（改行などは足さない。transformers 5.14.1 で確認）
- 窓 256 の文章モデル（gemma4-l256）で足りる: 約 117 ＋ 答え 96 以下。2 問目以降（同じ写真への追加の質問）は差分だけ送り、窓があふれたら写真から作り直す

## 3. 作るもの・変えるもの

### 3.1 端末のアプリ（`android_app/`、再ビルド 1 回にまとめる）

| ファイル | 変更 |
|---|---|
| `cpp/runner/job.cpp` の `generate_kv` | **画像の特徴を入れる**: job に `image_features`（float32 [M,1536] のファイル）があれば、プロンプトの画像トークン（258880）の位置に順に入れる（√1536 倍しない）。PLE はその位置だけ pad（0）の行。数が合わなければエラー。`dialogs` の要素を `{turns, image_features}` の形でも受ける（126 問の評価用） |
| `cpp/runner/vlm_prep.{h,cpp}`（新規） | 前処理: 縮小（**PIL の BICUBIC を固定小数点まで再現**）→ 黒い余白 → パッチ化 → ×1/255。`vlm_prep` の job（PC からの照合用）と JNI（画面用）の両方から呼ぶ |
| `cpp/edgeslm_jni.cpp`・`NativeBridge.kt` | `nativeVlmPrep(jobJson)` を追加（JSON で受けて JSON で返す＝今の約束どおり） |
| `RunnerService.kt` | `task == "vlm_prep"` はモデルを開かずに前処理だけ行う（`tokenize` と同じ扱い） |
| `VlmActivity.kt`（新規） | 画面: 撮る → 写真の表示 → 質問（入力欄と候補 3 つ）→ 答え（1 トークンずつ）→ 小さな 1 行 |
| `AndroidManifest.xml` | `VlmActivity` をランチャーの入口（「VLM デモ」）にする。カメラの権限は宣言しない（撮影はカメラアプリに頼む。MediaStore に保存させる） |
| `RunnerHoldActivity.kt`（新規、2026-09-29 夕方に追加） | **画面を前に出したまま job を動かす入口**。RunnerService を起こし、「実行中（経過秒）」を出したまま前に居続け、結果のファイルが書かれたら自分で閉じる。1.5GB を開く間（一時的に約 3GB）に画面が裏だと OS に止められる（6 章）ための対策。RunnerActivity（Theme.NoDisplay）は P0〜P4 の再現のため変えない |
| `VlmActivity.kt`（追加の変更） | 文章側のモデルを開いている途中に写真が来たら、開き終わってから画像エンコーダを動かす（読み直しと読み取りのメモリの山を重ねない） |

## 5. リスク

| リスク | 見分け方 | 手 |
|---|---|---|
| 端末の容量が足りない（文章側の写し 2.8GB） | setup で `df` を見る | 使わないファイルは写さない（L512 などは写さない） |
| 画像エンコーダの job の起動が遅い（別プロセスの起動 ＋ 読み込み） | 画面の 1 行 | 常駐させる（Phase 5） |
| カメラの写真が大きい（12MP） | 前処理の時間 | 読み込み時に 2 の累乗で縮めて（inSampleSize）から BICUBIC。PC の PIL とは入力が少し変わるが、品質への影響は小さい見込み |
| JPEG の復号が PIL と違う | — | 端末の中の差として受け入れる（Q14 は同じ RGB からの照合で見る） |
| 文章側と画像エンコーダを同時に開いたとき OS に止められる | 画面・logcat | 2-4 で同居は確認済み。止められたら画像エンコーダを先に動かしてから文章側を開く順に変える → **デモ画面は「文章側が開き終わってから画像エンコーダ」にした** |
| ★（実際に起きた）1.5GB を開く途中で OS（lmkd）に止められる | logcat の `lowmemorykiller: Kill 'org.edgeslm.vlm' … oom_score_adj 50 … device is not responding` | **画面を前に出したまま開く**（RunnerHoldActivity）。裏側で開こうとした 10 回中 3 回プロセスが消えたのが、前に出すと 5/5 回止められなかった（6 章） |

## 6. 結果（2026-09-29、[記録](../results/P3_20260929_device_vlm.md)）

| 問い | 結果 |
|---|---|
| Q13 端末の中だけで答えが出るか | **出る**（画面の照合。評価の写真で、モデルは 2 つとも NPU・strict）。カメラで撮る手順は人の手での確認が残り |
| Q14 前処理は PC と同じか | **108/108 でビット一致** |
| Q15 端末だけで 126 問 | **48/123**（同じ画像の特徴で PC の文章側 45/123、入れ替わり 8↑・5↓、符号検定 p=0.58。端末側の偶然の当たり 2 問を除くと 46）。PC では出なかった「画像が提供されていません」が 3 問 |
| Q16 待ち時間 | 最初の文字まで 8.3 秒（中央値）、答えの 1 トークンは中央値で画面 68.9ms・評価 77.7ms、画像の読み取り 1.17 秒（NPU 166ms） |

設計どおりに動いた。設計から変えたのは次の 2 つ:

1. **評価の job は画面を前に出したまま動かす**（RunnerHoldActivity）。1.5GB を開く間は一時的に約 3GB 使い（EdgeSLM_AndroidScale P2）、
   画面の無い Service（oom_score_adj 50）だと OS に止められることがある。画面が前（0）なら止められなかった（AndroidScale P3 で 25/25、今回 5/5）
2. **デモ画面は文章側が開き終わってから画像エンコーダを動かす**（カメラの間に止められて作り直されたとき、読み直しと読み取りを重ねない）
