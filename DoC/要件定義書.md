## 1. 目的

SD888 の NPU で、**画像を見て日本語で答える VLM** を動かし、4つの用途（汎用 VQA・キャプション／車室内・車外カメラ理解／OCR・文書・画面理解／連続フレーム・準リアルタイム）で
「どこまで使えるか・何が壁か」を実測で示す。

製品を作ることではなく、**VLM を NPU に載せる要素技術の確認**と、本番端末（v73 以降）へ持っていく判断材料を作ることが目的。

## 2. スコープ

| 含む | 含まない |
|---|---|
| 画像エンコーダ（ViT）と射影層の NPU 化 | 音声エンコーダ |
| 既存の Gemma 4 E2B の文章グラフへの接続 | 文章グラフの作り直し（Phase 1 の検算で必要と分かった場合のみ別途判断） |
| 日本語の評価セット（4用途・小規模）の作成と評価 | 学習（射影層の新規学習など）。予備案として記録だけ残す |
| 端末の新しいアプリ（既存アプリの複製） | 既存プロジェクト・既存アプリの変更 |

## 3. 構成

```
カメラ／画像ファイル
  │  リサイズ（解像度を固定。例: 336×480 → 630 パッチ）・16px のパッチに分ける（CPU）
  ▼
プロセス A: 画像エンコーダ（NPU）
  │  パッチの埋め込み ＋ 2次元の位置 → ViT 16層 → 3×3 平均プーリング → ×√768
  │  → embed_vision（RMSNorm ＋ 768→1536）          ※射影層は NPU か CPU かを Phase 2 で決める
  ▼  画像の特徴 N×1536（N＝70 / 280 など）
プロセス B: Gemma 4 E2B の文章部分（NPU、既存のグラフ）
     画像トークンの位置: inputs_embeds ← 画像の特徴、ple_tok ← pad（ID 0）の行
     文章トークンの位置: 従来どおり（端末のトークナイザで ID → 表を引く）
     位置・マスク: 従来どおり（連番・因果マスク）
  ▼
日本語の応答（端末のデトークナイザ）
```

プロセスを分ける理由: NPU の上限（dma-buf 約 1,710MiB）はプロセスごと。文章部分が 1,467〜1,485MiB を使うため、同じプロセスに ViT を足すと上限に近すぎる。
233MiB ＋ 1,467MiB の2プロセス同居は実測済み。

## 4. Phase の計画

| Phase | 内容 | 完了の条件 |
|---|---|---|
| **0** | 既存資産の棚卸し | **完了**（P0） |
| **1** | **PC で確かめる。** ①4用途の日本語評価セット（各 10〜20 問程度、正解つき）を作る ②HF（bf16）と QAT 模擬で、画像トークン 70 / 140 / 280 ごとの品質を測る ③「文章グラフは無改造で済む」を検算（HF の本来の経路と、`inputs_embeds`＋pad の PLE で1トークンずつ流す経路の logits を比べる）④画像の特徴と PLE の射影の値域が、既存グラフの量子化の目盛りに収まるか | ③で logits が一致（相対誤差 1e-4 以下）。②で「どの解像度なら用途に足りるか」の表ができる |
| **2** | **ViT 単体を v68 へ。** 解像度を固定（まず 70 トークン＝630 パッチ）、QAT の INT8 重みと活性の目盛りを書き込み、C-1/C-8/C-9/C-10 を機械的に確認、QAIRT で変換 | 全ノード HTP、PC（QAT 模擬）とのコサイン類似度 0.99 以上（目安）、1枚の時間を測る |
| **3** | **端末でつなぐ。** 新しいアプリ（Gemma4 のアプリを複製）で、プロセス A の出力を B へ渡し、画像つきで日本語の応答を出す | 同じ画像と質問で、PC と同等の日本語応答（評価セットの一部で確認） |
| **4** | **用途別の評価。** 評価セット全体・速度（ViT・最初の文字まで・tok/s）・メモリ・発熱・連続フレームでの持続 | 用途別の性能表 |
| **5** | **最適化。** まとめ食いの prefill グラフ、画像トークン数の削減、連続フレーム（前フレームの KV の扱い） | 準リアルタイムの目標値を達成、または限界値を把握 |

## 5. 目標値（案。Phase 1 のあとに見直す）

| 項目 | 案 |
|---|---|
| ViT 1枚（70 トークン） | 1 秒以内 |
| 最初の文字まで（70 トークン＋質問） | まず 8 秒以内（現状の形）→ まとめ食い後に 4 秒以内 |
| 生成 | 10 tok/s 以上（文章部分は既存どおり 13〜15 tok/s の見込み） |
| 精度 | 評価セットで PC（QAT 模擬）と同等。PC で正解し端末で落とす問題の数を数える（AndroidScale P4 と同じ見方） |
| 連続フレーム | 数秒に1回の説明を 10 分続けて、発熱による速度低下を記録 |

期限・成果物の形式（デモ動画・記録・同僚向け資料など）は未確定。

## 6. リスク

| # | リスク | 確かめ方・逃げ道 |
|---|---|---|
| R-1 | ViT の attention（系列長 630〜2,520）が v68 で重い・載らない（VTCM 4MB、C-8） | Phase 2 はまず 630 パッチ。重ければ ViT を2つに分ける／CPU に一部を逃がす |
| R-2 | 画像の特徴が、既存グラフの入口（PLE の射影）の量子化の目盛りに収まらない | Phase 1 ④で値域を確認。収まらなければ入口のかたまり（層0〜8）だけ作り直す |
| R-3 | 待ち時間（1トークンずつの prefill） | 70 トークンから始める。Phase 5 でまとめ食いのグラフ（1回 1.08 倍の実測あり） |
| R-4 | RAM 8GB（2つ目の大きなグラフが持てない） | ViT は小さい（約 150〜250MiB）ので同居できる見込み。prefill 用グラフは切り替え |
| R-5 | 小型 VLM の日本語 OCR の精度 | Phase 1 で PC の段階で測り、用途ごとに可否を判断 |
| R-6 | ViT の LayerNorm 相当（RMSNorm）・GELU・Softmax の 8bit 精度 | QAT の目盛りがあるので文章側と同じ見込み。Phase 2 で層ごとに誤差を見る |

## 7. 本プロジェクトの約束

- 既存プロジェクトのファイルは変更しない。道具は複製し、複製元と md5 を `DoC/引き継ぎ一覧.md` に残す
- 端末のアプリは新しく作る（パッケージ名は別。元のアプリと端末上のファイルに触れない）
- 開発したソースには設計書を作る。記録は `results/` に Phase ごとに残す
- 見立ては切り分けの実験で確かめてから記録する。報告した数字の誤りが分かったら訂正を残す
- 大きな変換（数十分以上）の前に、PC（Host）で崩れないことを確かめる
