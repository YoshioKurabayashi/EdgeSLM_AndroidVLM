## 3. グラフの形（2-1 で決めること）

### 3.1 入出力

| | 名前 | 形（70 トークン） | 型 | 中身 |
|---|---|---|---|---|
| 入力 | `pixel_values` | [1, 630, 768] | float32 | 0〜1。パッチ n = y·30 + x（左上から右へ・行ごとに下へ）、1 パッチの並びは (py, px, c)（HF の `convert_image_to_patches` と同じ） |
| 出力 | `image_embeds` | [1, 70, 1536] | float32 | 射影層の後。そのまま文章側の `inputs_embeds` の画像の位置に入れる（Phase 1 で確認済み） |

端末では、カメラの画像を 336×480 にレターボックスし（CPU）、この並びに詰め替えて渡す（Phase 3 で Kotlin に書く）。

### 3.2 グラフの中身と、HF からの書き換え

`app/pipeline/vit_graph.py` の冒頭に全部書いた。要点:

| 書き換え | 理由 |
|---|---|
| 位置の埋め込み・2 次元 RoPE の cos/sin を**定数**にする | 格子が固定なので位置も固定。Gather（表を引く）をグラフに入れない |
| 3×3 の平均を **reshape → ReduceMean ×2** で書く（4 次元まで） | 定数の行列（630×70）を持たない。量子化の工程で「QAT でない重み」として扱う手間も無い |
| プーリングの後の **×√768 を省き**、射影層の RMSNorm の eps を eps/768 にする | 数学的に同じ（RMSNorm(c·x; ε) = RMSNorm(x; ε/c²)）。演算と Q/DQ が 1 組減り、fp16 の区間があっても溢れにくい（精度の得ではない。7 章の StudyMemo を参照） |
| RMSNorm は Gemma4 と同じ形（Pow→ReduceMean→Add→Sqrt→Reciprocal→Mul） | QAIRT が RmsNorm に融合する形。C-11（x² の書き換え）は Gemma と同じく使わない |
| 注意は 4 次元の行列積 [1,12,N,64]、マスクなし | 双方向でパディングも無いのでマスクが要らない（C-9 に当たらない）。KV ヘッド＝Q ヘッドなので複製（Expand）が出ない（C-10） |
| k^T と v は行列積の右辺専用のテンソル | C-8（act×act の右辺は 8bit）を後処理で当てるとき、他の用途を巻き込まない |

### 3.3 重みと量子化の対応（2-2 の準備）

| 部分 | 重み（safetensors） | 量子化の方針 |
|---|---|---|
| パッチの埋め込み `input_proj` 768→768 | BF16（QAT ではない） | INT8 の出力チャネルごと（Gemma4 の PLE の射影と同じ「from_float」） |
| 16 層の q/k/v/o・gate/up/down（112 本） | **INT8・出力チャネルごと＋活性の目盛り 224 本**（全部 0 以外） | QAT の整数とスケールをそのまま書き戻す。入出力に u8 の SRQ |
| 正規化の重み | BF16 | C-13（int16 の対称） |
| 射影層 768→1536 | F32（QAT ではない） | from_float（INT8） |
| 位置の埋め込み・cos/sin（定数） | — | 活性と同じ 16bit（ORT は MatMul 以外の初期化子を活性の型で量子化する） |

## 5. v68 の制約の当たり方（見込み）

| 制約 | 画像エンコーダでは | 対策 |
|---|---|---|
| C-1 float の区間・入力 | 入力 `pixel_values` を最初に使うのは Sub（2·(p−0.5)）。量子化される | export で「最初に使う演算」を表示して確かめる |
| C-8 act×act の右辺 | q·k^T と 確率·v の 2 か所 × 16 層 | Gemma4 の downgrade_actact_rhs を流用 |
| C-9 マスク | マスクなし | — |
| C-10 Expand | 出ない見込み | export で演算の一覧を確かめる |
| C-12 embed_mode | context は 200〜300MiB の見込み（重み 144MiB） | 420MB までは embed_mode=1 で動いた実績。念のため 0 で作る |
| C-13 RMSNorm の gamma | 16 層 × 4 ＋ q/k_norm × 2 | Gemma4 の fix_norm_gamma（`norm\.weight` の名前で探す。名前が合うか 2-2 で確かめる） |
| NPU の作業メモリ（VTCM 4MB） | 注意のスコア [12, 630, 630] は u16 で約 9.5MB | HTP が分割する前提。遅ければヘッドを分けて書く（同じ計算） |
| **C-14 重みのスケールの下限**（2026-09-29 に端末で発見。本プロジェクトで新設） | パッチの埋め込み（float から INT8 に作り直す重み）に、重みがほぼ 0 のチャネルが 222 本。スケール 4e-6 未満のチャネルだけ端末で値が壊れた（PC の QDQ では壊れない） | 出力チャネルごとのスケールに下限（最大の 1/64）を付ける（`qat_inject_vit._from_float`）。quantize_vit で「最小/最大」を検査する。QAT の 112 本は最小/最大 0.09 以上で該当しない |

## 6. リスク

| リスク | 見分け方 | 手 |
|---|---|---|
| 残差の値が巨大（HF の pooler に「fp16 の範囲を超えうる」とある） | capture_vit の値の範囲 | 16bit でも潰れるなら、Gemma4 P0C のように巨大な次元を調べ、書き換えを考える |
| 量子化で特徴が崩れる | 2-2 の PC の QDQ と HF の cos、答えの点 | 較正の枚数、目盛りの取り方（MinMax 以外）、層ごとの切り分け（Oracle 実験） |
| 変換が通らない（演算・VTCM） | QAIRT のログ | 形の書き換え（ヘッドを分ける、行列積の形を変える） |
| 端末で遅い | 2-4 の時間 | 70 トークンのまま、Phase 5 で |
